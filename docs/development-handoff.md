# D16 通用开发交接清单

适用于所有网站的“批准输入→D16开发→独立验收→反馈处理”。生命周期、分支集成和发布以[开发流程](development-workflow.md)为准；开发方法以[内部执行](development-execution.md)为准。用[通用任务模板](templates/development-task.md)组织输入，用[任务记录](templates/development-task-record.md)保存事实，不另建重复账本。

本清单规定共同内容；阶段名称、外部状态字段、机器Schema和验收工具由所属策划接口补充。D23使用[D23交接适配](d23-gate-handoff.md)，其他网站不强制采用其Gate编号或工具。共同规则在此维护，专属文件不复制整套开发流程。网站冻结及特定约束仍按根规则执行。

## 1. 批准输入交给开发

发送方为业务/策划交付负责人或用户，接收方为准确定位的D16任务。目标是确定按哪个有效版本、为哪个网站实现什么、怎样验收及本次负责到哪一步。

| 输入 | D16接收检查 |
|---|---|
| 网站、语言、页面/功能、路径、范围与限制 | 与网站登记、现有代码和目标环境一致，不只给页面名称 |
| 当前批准入口、交付身份、版本/哈希及替代关系 | 来源可读取且组合有效；草稿标记结合后续有效批准解释，不按文件名或时间猜测 |
| 业务内容与行为合同 | 正文、模块顺序、字段语义、必需/可选、格式、链接动作、条件/空值/失败行为足够明确；不能只凭截图猜正文 |
| 视觉与交互状态 | 原始设计、响应式、菜单/弹窗/焦点等适用状态和共享样式来源；核对完整页面，不只首屏 |
| 资产和权属 | Logo、字体、图片/文件的版本、使用范围、所属网站及缺失处理；生产不依赖策划本机目录 |
| 路由、SEO与机器语义 | URL、语言、canonical、metadata、结构化数据、导航和索引阶段符合批准，不自行新增事实 |
| 共享与接收方行为 | 共享owner、按钮目标、字段基数、预填、可见行为与接收合同；核对语义和消费者，不发明参数 |
| 参考代码或原型 | 按来源明确哪些结果是批准合同、哪些实现仅供参考；未明确批准的示例不能自动成为批准依据或操作授权 |
| 接受条件 | 保留已有ID、预期结果、正负向/交互/隔离范围、失败判据及验收责任方；无ID时用明确条件，不伪造外部编号 |
| 依赖与开放项 | 上游页面、外部账户、数据、法律条件、责任方及后置依据；不得隐藏真实依赖或用假目标掩盖 |
| 交付与授权 | 接收目标、请求动作、授权范围、本次终点及下一责任方；批准内容不自动授权外发、远程写入或发布 |

业务方定义应有结果，D16按现有架构决定技术映射；已有有效技术合同按其范围继承，不改变批准语义。

### 接单结果

从[业务入口](business/README.md)定位网站、领域和相关流程，从[软件架构](software-architecture.md)定位模块、数据流及代码入口；业务目录未覆盖时直接引用有效交付包并记录缺口，不要求先整理整站业务。

在同一任务记录保存批准组合、授权、develop基线及任务分支、复用/扩展/新增判断、共享差异和消费者；在第3节建立“业务条件/原接受条件→架构模块与实现位置→测试层次、场景及预期结果”，实施后补齐证据。

接单结论分可执行、部分可执行、依赖步骤暂缓；明确每个缺口影响及责任方，只停依赖它的步骤。例如缺少真实邮箱验收不自动阻止布局开发。接单不是独立验收，也不证明已有共享实现符合要求；批准语义冲突返回业务决定方。

## 2. 开发交给独立验收

发送方为D16实施负责人，接收方为本网站指定验收者。交付必须可锁定“批准依据＋指定实现＋实际运行＋证据”。

| 输出 | 必须能确认的事实 |
|---|---|
| 批准与任务对应 | 网站/范围、有效批准版本、接受条件及明确差异 |
| 精确源码身份 | 分支、baseline/implementation commit、工作树状态；有未提交内容时提供差异快照/哈希；基础commit不冒充全部实现 |
| 证据清单 | 接受条件、证据路径、对应版本及适用范围；机器格式、哈希和证据提交要求按专属接口补充 |
| 实际运行 | URL、网站、环境、Build/部署身份、核验时间、启动/访问限制、保持与释放约定；本地生产模式不等于生产部署 |
| 数据与技术映射 | 业务语义→适用CMS/数据→接口/查询→校验→组件/路由；SEO、缓存、导航、表单和媒体位置 |
| 数据/配置身份 | 相关记录归属/状态、响应或合同哈希、配置位置与脱敏关联；非空配置不证明服务商或收件成功 |
| 逐项验证 | 条件、检查方法、日期、版本/环境、结果、未测原因与原始证据；TDD/测试/审查按内部执行要求引用 |
| 视觉、交互及影响面 | 适用原图和操作、数据异常/隔离/缓存/共享消费者回归；实际看图，不能只报测试数量或DOM断言 |
| 外部接收边界 | 模拟、实际接线、历史/当前provider接受、邮箱收件分别说明；未经授权不新增真实提交 |
| 恢复与剩余项 | 临时数据恢复、适用回退定位；实现、证据、跨页、外部及发布依赖分列影响与owner，不概括为全部未完成 |

### 交回前检查与缺项处理

1. 按统一执行流程完成适用候选验证，核对版本、测试、截图和数据恢复；已知范围内的实现缺陷先修复。局部交付明确“部分可验”和缺项，不宣称整体完成。
2. 身份不能锁定、运行不可访问或证据缺失时说明受阻条件；可审阅不受影响材料，不能签受阻项通过。允许后置的发布条件不自动变成本页代码缺陷。
3. 发送前固定接收目标和请求范围；准备材料、面板排队、发送、接单、验收分别记录。实际发送须有适用授权及工具或人工送达依据；工具不可用时如实说明尚未送达。
4. 按约定保持同一候选直到适用通过、退回或释放通知；不能保持或需要更换时说明受影响条件、提供新版本与运行身份，不让旧端口冒充原候选。反馈到达后保存精确验收对象和结论。

## 3. 退回、接收与后续集成

退回至少定位原条件/问题ID、现象、复现版本与环境、证据、预期和责任方。D16处理技术修复，业务事实/合同冲突交原决定方，验收者不直接改开发代码。

回复根因、最小变更、新源码/运行身份、定向复测和共享影响；继承旧证据说明依据，失效证据保留并标记替代。接受后记录哪些问题在哪个版本关闭、开放项及下一责任方。无新反证时停止重复返修，局部接受不等于整体验收或发布许可。

技术、验证、独立验收、集成、发布授权和部署分别记录；外部状态枚举只按所属接口使用。后续合并只执行[开发流程第6节](development-workflow.md#6-分支开发机器交回与串行集成)的任务→develop→main规则，不建立第二套队列。预发布使用main；CI/CD具体实现待预发布完成后讨论。进入集成资格不等于合并、push或发布授权。
