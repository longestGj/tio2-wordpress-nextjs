# 发布与故障修复执行规则

本文件依据 2026-09-14 发布恢复及既有测试失败清理的复盘，规定可检查的执行动作、验收条件和失败处理。适用于 D16 的发布准备、安装升级、CMS 合同迁移、故障修复与测试维护；具体网站、环境和写入授权仍按当次任务确定，不能将 MY 的现场策略默认推广到其他网站。

本文补充[开发交付流程](development-workflow.md)和[独立发布流程](release-workflow.md)，不增加发布授权，不替代[发布架构](release-architecture.md)、[管理员安装说明](production-installation.md)中的具体状态与动作。用户当前明确要求与已有有效授权优先；规则检查不要求对同一授权重复确认。

“必须”是适用任务的执行或设计验收要求，不表示相应通用能力已经实现或安装。实际能力以准确代码、现场状态和对应验证回执为准。尤其是通用 CMS 合同迁移、替代收件证据，不能因本文件存在而调用尚未实现的入口。

## 使用方法与职责

任务负责人按触发条件选择规则，在现有[开发任务记录](templates/development-task.md)、[开发回执](templates/development-receipt.md)或[发布候选回执](templates/release-candidate-receipt.md)中引用规则编号。记录 `适用／不适用及原因、证据位置、通过／失败／未执行、未决项责任方`；不另复制一套任务状态，不要求日常文档修改执行全部发布检查。

开发负责人负责实现与相关回归，独立复审者核对准确实现和证据，发布负责人只消费获准候选并执行适用发布动作。发布侧发现代码缺陷时保存阻断证据，退回开发流程；不在发布工作区临时改业务实现。

| 规则 | 触发条件 | 主要责任方 |
| --- | --- | --- |
| [R01 发布对象](#r01) | 开始发布、重新冻结候选 | 发布负责人 |
| [R02 故障证据](#r02) | 诊断构建、安装、发布或运行故障 | 当前诊断负责人 |
| [R03 安装生命周期](#r03) | 修改安装、升级、恢复实现 | 开发负责人、独立复审者 |
| [R04 合同迁移](#r04) | 新 CMS 合同不能接受现有数据 | 开发负责人；执行由获授权发布负责人负责 |
| [R05 真实消费者](#r05) | CMS、共享依赖或读取链变化 | 开发及发布负责人，各自验证所处环境 |
| [R06 失败策略](#r06) | 建立事务或修改恢复策略 | 开发负责人、获授权管理员及发布负责人 |
| [R07 状态消费者](#r07) | 状态、日志或证据格式变化 | 开发负责人、独立复审者 |

| [R09 版本绑定](#r09) | 审查、合并、打包或复用证据 | 产生与消费证据的负责人 |
| [R10 验收终点](#r10) | 规划需要业务或收件确认的验收 | 发布负责人 |

<a id="r01"></a>
## R01：发布前固定对象、来源、写入范围和终点

**必须执行：**在写入前记录网站／主体、准确目标实例、前端 commit、内容来源实例及导出哈希、CMS 插件制品及哈希、服务器实际启用的安装程序版本、配置身份、允许修改的对象和本次终点。不涉及的对象写“不涉及”，不为补齐字段扩大范围。

**通过标准：**来源与目标可从运行身份、制品和回执核对；每个写动作均落在授权范围。不能仅用“发布 main”“更新网站”作为最终执行描述；不能凭目录名判断数据库身份。用户已选定内容来源时，无需逐页重复业务差异审批，技术身份、完整性和兼容检查仍须执行。

**失败处理：**来源不明、制品漂移或写入越界时停止对应写动作，保留已完成的只读核对；不因报错而顺带升级其他对象。

**本次适用示例：**MY 内容来源明确为 main 预发布数据库，开发数据库不参与。前端构建依赖 CMS，不代表前端发布获准导入数据库。后续任务仍按各自来源重新绑定。

<a id="r02"></a>
## R02：先记录故障证据，再提出修复动作

**必须执行：**每个阻断记录失败对象、失败动作、实际版本和环境、原始错误及日志位置、已确认原因与待验证假设。日志须脱敏；不要复制密钥或用户隐私。

**通过标准：**升级、迁移或回滚建议有直接证据支持。`版本校验拒绝`不能直接证明 CMS 未升级，`HTTP 500`不能直接证明内容不兼容。修复后重跑原失败动作，并记录同一故障是否消失；无关健康检查不能代替复验。

**失败处理：**证据不足时继续只读诊断或隔离复现，不把假设写成根因，不把升级当默认诊断步骤。

**本次适用示例：**权限故障需要 UID 33 能加载 WordPress、原失败 GraphQL 查询成功、受影响页面构建通过，才能闭合该故障；后续不同错误另建记录。

<a id="r03"></a>
## R03：安装器覆盖已有环境和中断恢复

**必须执行：**修改安装、升级或恢复代码时验证下列适用路径，并明确不适用的原因。

| 场景 | 验收结果 |
| --- | --- |
| 首次安装 | 完成且保存准确安装、资源和制品身份 |
| 已完成安装再次升级 | 识别旧安装，按升级流程执行 |
| 相同操作重复提交 | 不重复创建资源，不破坏当前状态 |
| 执行中断后重新进入 | 依据持久状态选择明确续接、恢复或拒绝动作 |
| 已有合法维护规则 | 核验归属与准确内容后按实现复用 |
| 未知或被修改的规则 | 拒绝并指出冲突对象 |
| 升级失败 | 按既定策略恢复或保留现场，记录实际结果 |

**通过标准：**成功与失败路径都有可检查的资源身份和状态；既有合法资源不会仅因存在而被误判。

**失败处理：**不得删除已有状态文件、维护规则或旧容器来绕过识别。需要修程序时回到开发流程，以原失败场景验证补丁。显式恢复和资源清理由已有流程决定，不因本规则禁止合法受控清理。

<a id="r04"></a>
## R04：CMS 合同升级必须包含完整迁移路径

**必须执行：**新合同不接受现有数据时，执行前固定支持的旧合同版本、目标版本、受影响页面、正文及关联／审核等附属数据、插件切换与迁移顺序、备份及恢复窗口、迁移后验证方法。使用旧版数据副本在隔离环境验证完整路径。

**通过标准：**准确识别旧数据，迁移输入包含新合同所需全部字段，结果通过新合同；重复执行不继续改变数据，无关页面与其他网站数据不变。异常测试验证事务和既定恢复策略，不只验证成功路径。

**设计约束：**普通内容写入与合同迁移使用各自的验证入口。旧数据不符合新合同，不能因此无法进入专用迁移路径；迁移仍须严格校验旧版本、网站身份、授权和目标输入，不能宽泛关闭校验。不得把 SQL 或任意元数据直接塞入不支持它们的普通内容包。

**失败处理：**不存在兼容路径或缺少附属数据时停止升级／迁移写动作，先补实现和隔离验证。不得以“先升级插件、再构建看看”代替迁移计划。

**能力边界：**本次 Resource 定向脚本只证明该次五页十条元数据迁移，不代表已实现通用迁移能力。数据库重新开放写入后，不得用历史整库备份覆盖后续数据，详见[内容发布](content-release.md)。

<a id="r05"></a>
## R05：以真实运行身份验证受影响消费者

**必须执行：**按变化的技术合同选取验证对象，记录页面／查询及选择依据。每个受影响合同至少有实际消费者；共享变化增加受影响网站回归，直接受影响页面按任务接受条件验证。

验证链为：`实际运行用户能读取插件 → WordPress 加载 → 实际 GraphQL 查询 → DTO 验证 → 页面构建或渲染`。数据库就绪验证使用实际业务账户、目标数据库和对应连接方式。

**通过标准：**每一层均有对应证据。root 加载不代替 Web 用户加载；HTTP 200 不代替 GraphQL 无错误和数据正确；HOME 通过不代替 Resource 等其他合同；数据库进程存活不代替业务账户可用。页面渲染通过不自动等于视觉或业务验收。

**失败处理：**定位失败层并修复，重跑相关链路；不能通过减少抽样范围避开已经暴露的错误。

<a id="r06"></a>
## R06：分别固定前端、CMS、内容和配置的失败策略

**必须执行：**建立事务时记录前端自动回滚或保留现场、CMS 插件恢复、数据库内容恢复窗口、配置恢复规则；绑定网站、事务和实际支持的配置入口。策略修改后验证受影响失败阶段。

**通过标准：**关闭前端自动回滚不会改变其他对象策略；禁用时不自动切回旧前端、不清理诊断现场，仍保留受控显式恢复能力。当前 MY 策略绑定 releaseId，不能默认视为永久全局设置；其他事务按其有效策略执行。

**失败处理：**状态不明先读持久 `status`；不得根据 SSH 退出码猜测状态。`RECOVERY_REQUIRED` 不得通过盲目重跑、重复激活或改状态文件绕过；按对应恢复流程处理。策略文件缺失、变更或不匹配时按实现拒绝，不静默切换策略。

<a id="r07"></a>
## R07：状态与证据格式变化必须验证所有消费者

**必须执行：**列出状态／证据的写入方和读取方，修改时检查跨程序链路。例如发布控制器生成恢复证据、程序升级器读取该证据、后续发布再检查当前状态。

**通过标准：**合法自动回滚、显式回滚证据均被对应消费者识别；缺失、损坏、错误事务和跨站证据被拒绝。旧格式兼容条件明确，不得把任意解析失败当作旧格式。新状态必须定义合法后续动作，或明确进入受控恢复。

**失败处理：**一个程序完成而另一个拒绝时，保留双方准确状态和证据，修复兼容合同；不得改写现场回执使检查通过。

<a id="r08"></a>
## R08：测试失败必须分类、处理并保留边界

**必须执行：**按根因记录处理方式，不以“既有失败”作为永久豁免。

| 类别 | 处理与验证 |
| --- | --- |
| 程序行为错误 | 修实现，保留可复现该故障的回归 |
| 已批准行为变化、预期过期 | 引用批准依据更新预期，保留有效限制 |
| 测试连接错误环境 | 修身份与隔离，核对实际目标 |
| 真实子进程时限不合理 | 设置有界时限，保留永不返回和清理失败用例 |
| 历史制品与当前源码混用 | 对照准确历史版本，当前版本另行验证 |
| 外部前置条件缺失 | 标明未执行、条件、影响和责任方 |

**通过标准：**日常运行与改动及依赖直接相关的测试；明确要求清理全量失败时，关闭记录须有一次全量零失败。通过、失败、跳过分别统计，生成目录中的旧测试副本不计入当前源码测试。

**失败处理：**不得为通过而新增跳过、删除有效断言或无限增加时限。未解决项有具体责任与影响；历史来源不能代替处理结论。本规则不要求每次文档或低影响修改重跑全量测试。

<a id="r09"></a>
## R09：审查与通过证据只绑定准确版本

**必须执行：**证据绑定源码 commit／tree、适用制品及内容哈希、配置与运行环境身份、验证日期、命令及结果。代码、内容或配置变化时判断证据失效范围，重新验证受影响部分。

**通过标准：**合并前核对来源、目标 HEAD 和工作区；合并后确认准确审查实现已包含，运行必要集成回归。打包验证准确制品字节；Windows 换行转换不得使工作区验证与制品哈希脱节。归一化前须确认不会覆盖语义修改。历史制品检查只证明该历史制品。

**失败处理：**身份漂移时形成新候选和相应证据，不给旧候选的邮件、构建或页面结果改名。合并冲突解决改变已审实现时重新审查相应变化，不能沿用原批准宣称新树通过。

<a id="r10"></a>
## R10：真实验收前固定证据要求和完成状态

**必须执行：**真实表单或收件测试前，按当前完成合同说明需要的证据、保存方式及缺失证据时可达到的状态。页面成功、服务商接受、实际收件分别记录；复用用户已有有效授权与明确证据偏好，不反复索取已拒绝保存的材料。

**通过标准：**程序完成状态与实际具备的证据一致。若当前合同要求原始邮件，用户确认收到可以记录为收件事实，但不能伪装为已有原始邮件或完整 completion 证据。原始邮件的保存或不保存按用户要求处理，不将隐私材料写入 Git。

**失败处理：**证据不满足当前完成合同时，记录已达到状态和具体未决项，不伪造文件、不改状态绕过。若用户要求支持替代收件证据，须正式修改合同、生成器和验证器，经测试及适用安装后启用；本文件不直接启用该能力。

**本次适用示例：**用户确认三封邮件 10:22 收到且不保存 `.eml`，记录收件事实，未生成要求原始邮件的 completion 证据；当次服务器保持 `PUBLIC_VERIFIED`。这不是后续事务的默认验收配置。
