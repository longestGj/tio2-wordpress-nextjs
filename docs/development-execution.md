# D16 内部开发与测试执行

本文件只描述任务分支上的 TDD、单元/集成/任务 E2E、技术复审和开发环境。开发职责与 `develop` 合入见[开发交付流程](development-workflow.md)；预发布、候选包和生产动作见[独立发布流程](release-workflow.md)。

故障诊断、真实消费者验证和测试失败分类分别执行[规则 R02](release-engineering-rules.md#r02)、[R05](release-engineering-rules.md#r05)、[R08](release-engineering-rules.md#r08)；检查范围按本次变化确定，不将全量测试作为日常文档修改前置条件。

## 1. 任务记录

每个任务在开始时固定网站、任务主体、批准输入、接受条件、`develop` 基线、分支、允许修改路径、消费者、开发环境和授权边界。记录中把“要求什么”“由哪个模块负责”“怎样观察结果”连起来，避免只列文件或测试数量。

状态分别记录：未开始、实现中、技术验证通过、独立代码复审通过、返修中、已合入 `develop`。开发记录不推断后续环境状态。

## 2. TDD

行为新增、缺陷修复和有风险的重构执行红绿重构：

1. 先从批准条件或明确技术合同写出一个能观察目标行为的测试。
2. 运行测试，确认它因行为缺失或错误而失败；语法、导入和环境故障不是有效红灯。
3. 写让该测试通过的最小实现。
4. 重新运行同一测试并确认通过，再运行直接相关回归。
5. 需要时重构，并保持测试通过。

已有行为本来正确时，已有测试的通过只能记为基线或回归，不能倒写成红灯。缺少历史红绿证据时标为后补回归。测试不得调用被测逻辑生成预期，也不得用源码字符串或无行为的 mock 代替真实结果。

## 3. 测试层次

| 层次 | 适用问题 | 证据边界 |
|---|---|---|
| 单元 | 纯函数、DTO、校验、状态转换、错误映射 | 快速定位单一行为；不证明组件已接线 |
| 集成 | 查询到 DTO、API 到服务、组件到接收适配器、CMS scope | 观察真实组件连接；模拟外部端时明确模拟边界 |
| 任务 E2E | 本次改动影响的关键用户旅程、路由、表单状态或跨页关系 | 绑定实际任务 Build、网站、URL、数据和视口 |
| 人工视觉/交互 | 完整页面、响应式、焦点、菜单、弹窗和图片 | 保存实际看到的状态；不由 DOM 焦点或截图数量代替 |

每项接受条件必须有验证去向，但不要求机械地同时建立所有层次。共享实现先验证本身，再对受影响网站运行有限消费者回归。真实外部提交需已有适用授权，并把 provider 接受、Thank You 和实际收件分别记录。

## 4. 开发环境

| 用途 | 身份与边界 |
|---|---|
| 多站开发 | `tio2-a` / `tio2-b` / `tio2-my` 使用登记的网站身份和各自端口，不跨站 fallback |
| 人工 feature runtime | 从租约池申请端口，绑定网站、worktree、Build 和保持/释放条件 |
| 自动化 Next/HTTP fixture | 优先使用 OS 端口 `0`；需要数字端口时使用自动化租约池 |
| 开发 WordPress | canonical 开发 Compose 与数据；共享写入串行并可恢复 |
| 隔离 WordPress 测试 | 使用唯一 `d16-test-*` 项目；数据库不暴露主机端口 |

固定端口、租约、owner 核对和恢复命令见[运行端口操作手册](runtime-ports.md)。只停止本任务启动且身份核实的进程；不能杀掉端口占用者、重建别人的 Compose 项目或清理共享卷。

每个并行任务使用独立 Build 目录、测试输出和运行身份。worktree 只隔离源码，CMS、端口、Docker 项目和证据仍需单独隔离或串行。

## 5. 选择与运行检查

正常开发运行与变化及依赖直接相关的检查：

- TypeScript、PHP 或 Python 合同变化运行对应单元和类型检查；
- 组件连接或数据流变化运行集成测试；
- 用户可见流程变化运行少量关键 E2E 并查看适用视觉状态；
- 共享基础设施变化核对消费者并运行有限回归；
- 纯文档变化只检查链接、差异与规则一致性。

命令回执记录工作目录、代码 commit、网站、环境、前提、执行日期、通过/失败数量、跳过及原因。平台设施不可用导致的跳过如实报告，不能改写为零跳过。

测试失败先判断行为缺陷、测试缺陷还是环境前提。行为缺陷先写或保留能复现它的失败测试，再修复；偶然重跑通过不关闭问题。环境失败保留日志并只阻止依赖该环境的结论。

## 6. 技术复审

Gate8 冻结 BASE/HEAD 和证据后调用独立代码复审。复审检查批准范围、架构边界、测试真实性、错误路径、跨站隔离、共享消费者和未决项。审查者返回可执行问题或通过结论，不直接修改业务代码。

返修必须形成新的准确 HEAD，并运行针对问题的测试和受影响回归。复审通过只证明该开发候选具备合入 `develop` 的条件；Gate8 仍需核对实际合并结果并写开发回执。

## 7. CI 与恢复

当前仓库提供可显式调用的测试、构建、运行控制器和证据脚本；文档存在不表示提交触发器或远程 CI 已安装。开发 CI 的边界是任务分支与 `develop` 合并结果，检查集合按影响面选择。

长任务记录 BASE/HEAD、已完成步骤、最近命令结果、返修轮次和开放决定。恢复时先用 Git 与实际运行身份核对台账，不重复执行已经稳定完成的工作，也不覆盖其他任务的未提交修改。

开发 Build 和临时数据不是发布制品。开发侧只提供 `MERGED_TO_DEVELOP` 回执和可追溯证据，供独立发布流程在新的指令下重新冻结和验证。

## 10. 两套本地环境

开发环境用于任务分支上的修改、调试和验证；本地预发布环境用于独立发布流程冻结后的稳定候选。两者必须使用不同源码身份、端口、Build 目录、CMS 数据卷、配置和证据目录，并能分别停止和恢复。

| 维度 | 本地开发环境 | 本地预发布环境 |
|---|---|---|
| 源码 | 从 `develop` 创建的任务分支/worktree，可记录清楚的未提交修改 | 发布负责人冻结并准确合入的干净 `main` commit，经 Git archive 固定 |
| Next.js | `next dev`；必要时在任务目录 build/start | 生产模式 build/start，不用 `next dev` 充当候选 |
| 网站端口 | 多站固定 3001/3002/3003；人工或自动化使用租约/动态端口 | `tio2-my` Next `127.0.0.1:3100` |
| CMS | 开发 WordPress `127.0.0.1:8080`；共享写入串行或另行隔离 | 独立 WordPress `127.0.0.1:8180`，MariaDB 不暴露主机端口 |
| 数据与上传 | 开发栈自己的 volume 和夹具 | 专用 prerelease volume，不共用开发库或 uploads |
| 配置 | 任务或开发栈的忽略文件 | `.env.prerelease.local` |
| 证据 | 任务 commit、Build、端口、数据和测试结果 | 每 run 的 commit、archive、Build、CMS、配置和回执身份 |
| 外部副作用 | 优先模拟；真实动作依适用授权 | 普通测试禁止真实表单；独立实发入口依明确授权 |

开发侧不修改 `main`，也不启动本地预发布。预发布只在独立发布指令后由发布负责人建立。环境入口和具体命令分别见[运行端口操作手册](runtime-ports.md)与[预发布环境说明](prerelease-environment.md)。

固定端点冲突时核对 owner 并保留占用者，不能自动杀进程、重建另一任务的 Compose 项目或清理开发/预发布持久卷。普通 E2E 使用实际分配的 loopback URL；缺失身份直接失败，不回退历史固定端口。

## 11. CI/CD如何接入

仓库中的 CI/CD 是显式调用的检查与环境控制器；文档不表示远程平台、提交触发器或自动晋级已安装。开发和发布使用两个入口：

```text
开发：任务分支 TDD / 单元 / 集成 / 任务 E2E
  -> Gate8 调用独立代码复审
  -> Gate8 准确合入 develop
  -> MERGED_TO_DEVELOP 回执

发布：独立发布指令
  -> 冻结 develop / 核对回执和实际差异 / 发布侧集成 E2E
  -> 准确合入 main / 本地预发布 / 分类与打包
  -> 另有生产授权时执行生产三道门
```

开发 CI 只验证任务分支和 `develop` 合并结果。发布负责人重新验证冻结候选，不把任务分支旧 PASS 当成发布侧集成证据。发布侧失败保留准确候选与日志并退回 Gate8；形成新的开发回执后再由新的独立发布候选继续。

每组检查记录工作目录、网站、BASE/HEAD、环境、命令、超时、结果、跳过和证据位置。源码、数据、配置、依赖或测试变化使旧结论失效时，只重跑受影响范围；反复运行直到偶然通过不能关闭失败。

## 12. 现有能力与自动化缺口

| 能力 | 当前已有 | 边界 |
|---|---|---|
| 开发运行 | canonical 开发 CMS、多站入口、端口租约、owned E2E | 核对 owner、网站、Build、数据模式和清理范围 |
| 自动化隔离 | 动态端口、唯一 Docker 项目和测试输出 | 共享 CMS 写入仍须串行和恢复 |
| 本地预发布 | 独立 Compose、`scripts/prerelease.ps1`、健康与 smoke 入口 | 由独立发布流程显式调用；`HEALTHY` 不等于验收通过 |
| 固定候选 | 干净 `main`、源码 archive、Build/CMS/run 身份 | 候选变化后另建 run，不把旧 Build 绑定新 commit |
| CI 检查 | Vitest、Playwright、构建及合同命令 | 检查集合和门禁编排未自动化 |
| 生产工具 | 项目级发布流程、固定控制器和阶段一前台能力 | 与开发分离，仍需目标环境的明确授权 |

`runtime:status`、`prerelease:status` 和预发布 `start` 可能创建本地身份证据、临时工具容器或持久环境，不能称为纯只读。真实表单开关不授予外发权限。`verify:root-only` 继续要求单独明确授权。

## 13. 制品、数据与恢复

- 开发 Build 不直接搬入预发布；发布负责人从准确干净 `main` 和预发布配置重新构建。
- 保存源码 commit/archive hash、依赖依据、Build ID、CMS/seed/config 身份、测试版本、命令、结果和 run ID；测试和运行必须绑定同一候选。
- 开发数据库不覆盖预发布。版本化 seed 或迁移进入候选时，核对目标 scope、兼容性和恢复要求。
- 本地预发布候选不直接编辑；代码缺陷回 Gate8，形成新的 `MERGED_TO_DEVELOP` 回执后再冻结新候选。
- 正常停止保留预发布数据；显式 reset 只清理准确归属的预发布资源，不触及开发或其他任务环境。
- 源码快照不等于数据库恢复。数据变化的恢复同时考虑兼容源码、备份、配置和写入状态。
- 生产配置可能影响构建输出，本地预发布 Build 不能无条件搬入生产。生产制品、备份和回退遵守独立发布流程与目标网站运行手册。
