## 1. 目标与承载方式

每项开发任务建立一条可追溯关系：批准行为/技术要求 → 架构责任位置 → 实施任务 → 测试与检查 → 当前版本证据。以[现有任务记录](templates/development-task-record.md)或主回执承载，不新建一套竞争状态或重复批准源。

### 可交付范围怎样判定

| 本次对象 | 完成依据 | 不能据此推导 |
|---|---|---|
| 开发实现 | 适用合同已映射、实现及测试成立、技术审查/实际页面自检完成、未决项准确 | 独立验收或develop/main组合通过 |
| develop/main组合 | 已获授权集成，记录前后HEAD且影响面回归成立 | 预发布环境或全站验收通过 |
| 预发布候选 | 精确run/Build/CMS/测试版本绑定，健康及冒烟成立，适用全站条件逐项有证据 | 生产部署、真实收件或索引授权 |
| 发布 | 目标与授权明确，操作完成且目标环境验证/运行交接有依据 | 所有后续观察项已经结束 |

“全站”指本次网站发布范围内的页面/语言、共享组件和关键跨页旅程清单，不是每页机械执行相同矩阵。清单从当前批准路由/交付范围建立：逐项列必须覆盖的条件、检查方式、可继承的精确证据及未测影响。代表页面冒烟不能自动覆盖未检查页面；其他网站与尚未纳入范围的功能不混入结论。

- Agent承担结果、判断和协调；Superpowers提供设计、计划、实现、测试、调试和审查的方法。
- D16现有开发任务承担主控职责；实施与审查按适用技能调用临时通用子代理。职责不等于常设Agent，不新增项目专属Agent配置或Skill。
- 一项任务可以包含多种职责；独立审查者必须与被审实现作者不同，不能仅切换角色名称审查自己的作品。
- 任务复杂度决定过程规模；简单修复可在同一记录中合并设计、计划和检查。已有有效设计与授权直接复用。
- 本文件整合开发执行方法，不启动具体页面、历史任务、自动调度服务或部署。

2026-09-08补充：用户指出缺少CI/CD，并要求本地开发环境与本地预发布环境两套环境。第10–13节将现有环境入口接入内部执行流程，区分已实现命令、目标流水线合同及尚未实现的自动编排。

## 2. D16内部职责

| 职责 | 由谁承担 | 必须完成的判断/输出 | 边界 |
|---|---|---|---|
| 开发主控 | 当前D16开发任务 | 锁定网站、批准基线、授权和环境；组织架构、计划、影响分析；接收结果并维护任务记录 | 不能用子代理自述代替核对，不能改策划批准事实 |

| 实施与测试 | 主控直接执行，或SDD临时实施者 | 按任务实现；编写有价值的单元/集成/E2E测试；运行、自检、修复；返回精确差异和证据 | 测试与实现一起交付，不由测试角色兜底补完所有测试 |
| 独立技术审查 | 适用Superpowers审查流程中的不同临时审查者 | 给出需求符合性与代码质量结论，同时核对测试边界、断言和遗漏风险 | 只读；不替代策划独立验收；不为测试再默认增加一名重复审查者 |
| 运行与完整页面自检 | 主控负责组织，授权内可委派采集 | 核对实际Build/网站/数据，执行适用浏览器检查并实际看图，检查恢复 | 启动、测试数据和输出须隔离；模拟接收不能声称真实收件 |
| CI/CD与环境管理 | 主控负责，本地集成任务串行管理develop与main晋级；脚本执行确定性动作 | 定义检查范围与前提、串行集成、预发布候选构建、健康/验收、失败与恢复记录 | 不新增常设Agent；自动检查不授予合并或发布权限；只能操作本任务拥有的环境 |

主控可直接完成小任务的设计、实现与测试；需要独立技术审查时使用不同执行者。SDD要求的逐任务审查及最终分支审查按当前技能执行；测试充分性纳入这些审查，不再平行复制一套同范围审批。

## 3. 执行顺序与进入条件

| 环节 | 实际工作 | 适用Superpowers | 进入下一步的依据 |
|---|---|---|---|
| 接单 | 读取批准合同、现有共享实现、Git与运行状态，识别缺项 | using-superpowers | 身份和目标明确；缺项只阻止依赖它的步骤 |
| 技术设计 | 明确模块责任、数据/接口、scope、失败与恢复、共享消费者 | brainstorming | 已有批准直接继承；技术方案足以支撑实施，语义冲突已定位 |
| 测试策略与计划 | 将接受条件映射到实现位置和适用测试；确定真实/模拟边界 | writing-plans，TDD方法 | 每项条件有检查办法，关键依赖、测试前提与风险明确 |
| 建立工作现场 | 复用或创建适用隔离；确认基线与进程身份 | using-git-worktrees | 不覆盖其他任务；端口、Build和测试输出不冲突 |
| 实施 | 按行为执行红→绿→重构，逐项完成；错误先调查根因 | TDD、systematic-debugging；SDD或executing-plans | 当前行为及相关检查成立，无被忽略的阻塞问题 |
| 技术审查 | 查要求、差异、真实测试对象、覆盖缺口及共享影响 | requesting-code-review、receiving-code-review | 适用问题已处理；未决项及其影响明确，不夸大完成范围 |
| 当前候选验证 | 目标构建/运行、关键E2E、视觉与专项检查，核对证据身份 | verification-before-completion | 适用条件有当前证据；环境受阻项明确为未验证 |
| 技术交付 | 回执、证据、停止点和下一责任方；按原流程交回 | finishing-a-development-branch（分支收尾适用时） | 技术结论与版本绑定；外部验收/合并/发布状态保持独立 |

这里的顺序允许循环：新证据可以触发设计或计划的局部调整，测试与实施持续交替。不是“所有代码写完以后才交给测试”。审查也可以发生在任务之间，不必全部留到末尾。

新子系统、共享接口或跨站数据流变化应记录架构决定；现有页面内局部修复通常只需记录影响位置与理由。不要把每个组件拆分都升级成架构审批。

## 4. 技术架构最小内容

现有系统结构统一见[当前软件架构](software-architecture.md)。本节只规定一次任务怎样记录架构变化，不作为当前软件模块、数据流或生产部署的事实来源。

仅记录本次新增/改变的内容及有效继承来源：

1. 业务/内容语义如何映射到CMS、查询、DTO、组件、路由和SEO输出。
2. 每个受影响模块负责什么；消费和产出什么接口；哪些既有能力可复用。
3. 网站身份如何贯穿查询、缓存、路由、媒体、表单和配置；不跨站fallback。
4. 正常、缺失、损坏、错误归属及外部失败的适用处理与恢复；不凭空增加业务行为。
5. 共享消费者与兼容要求；局部变化为什么不会破坏冻结或已接受的其他实现。
6. 测试替身放在哪个边界，哪些必须连接真实组件/运行环境，怎样避免真实业务副作用。

Next.js相关实现仍先读取仓库安装版本的适用指南。框架默认行为、Skill示例和原型片段不能替代当前项目合同。

## 5. 分层测试与其他质量检查

测试层次按实际执行边界判断，不能只看目录名、文件名或使用了Vitest/Playwright。

| 层次/检查 | 本项目适用对象 | 证明范围与限制 |
|---|---|---|
| 单元 | DTO校验、预填、scope判断、payload组装、状态转换等有行为的模块 | 覆盖分支和边界，不证明完整CMS或浏览器链路 |
| 集成 | 查询与客户端/DTO、路由与内容映射、缓存标签/更新、表单适配器协作 | 说明连接的真实组件、模拟的依赖；MSW拦截GraphQL不等于真实WordPress验证 |
| 本地运行集成 | 指定网站的真实CMS/API/Next.js路径与适用数据恢复 | 需核实数据、配置和运行身份；有写入先确认授权及恢复，非默认只读 |
| E2E | 浏览器访问页面、导航、表单失败/恢复与关键用户旅程 | 记录流程起止点及被替换边界；只测单个页面元素不自动构成完整业务E2E |
| 视觉/可访问性 | 批准画面、响应式、可见焦点、原生缩放及其他合同状态 | 实际操作和看图；DOM焦点、截图已生成、axe计数均不能单独替代完整判断 |
| SEO/性能/安全/可靠性 | 当前变更涉及的metadata、索引保护、加载、隔离、外部错误等 | 按合同与风险选择，不能无依据自创阈值或默认对每页开展全套专项审计 |

当前仓库已有Vitest（单元与集成）、Testing Library、MSW及Playwright入口：见[package.json](../package.json)、[Vitest配置](../vitest.config.ts)、[Playwright配置](../playwright.config.ts)。这只是工具与组织基础，不代表所有条件已经覆盖或当前测试通过。

样本说明：`tests/integration/wordpress/queries.test.ts`使用MSW拦截网络；`tests/unit/rfq/malaysia-rfq-receiver.test.ts`注入fetch替身。这些测试可以验证真实查询/适配逻辑，但不能证明真实CMS或provider已接收。按任务读取具体测试再决定命令，不迁移目录来制造分层已完成的印象。

### E2E的定义与证据

E2E从用户或外部调用者的入口出发，经过系统实际协作的相关环节，验证最终可观察的业务结果。必须明确流程起点与终点、真实连接和模拟边界，并断言业务结果。使用Playwright、打开页面检查标题、按钮可点击或接口返回200，本身不足以证明完整业务流程。

例如：产品页→询盘页正确预填→填写并提交→看到正确结果，可以验证浏览器询盘流程；若模拟Web3Forms，必须标明外部接收边界被替换，不能证明实际发送或邮箱收件。提交→真实服务商接收→指定邮箱收到正确内容才覆盖实际收件链路，须有适用授权及收件证据。受控CMS更新→缓存刷新→浏览器看到新内容也是E2E，不要求所有E2E都从浏览器操作开始。

每项E2E记录：起点、终点、业务预期、真实环节、模拟环节、网站、源码/Build、数据与配置身份、执行命令/操作、实际结果和证据。环境失败、未运行或跳过不能写成通过；模拟范围不能扩张为真实外部结果。

| 阶段 | 必须验证的对象 | 环境与结果要求 |
|---|---|---|
| 任务分支→develop | 与任务及共享影响相关的关键流程E2E | 开发环境中的准确任务候选；已有用例足够则复用，行为变化未被覆盖时补充 |
| develop→main | 组合后的关键跨功能、跨页面流程及集成回归 | 开发环境中的精确develop候选；不能只汇总各任务旧PASS |
| main本地预发布 | 预发布实际配置、CMS、构建及本批次关键业务流程 | 干净main构建后验证；开发证据不能替代环境差异验证，代表性冒烟不等于完整验收 |

E2E范围由业务流程与影响面决定，不要求每次跑全站所有用例。以上测试要求当前生效，CI/CD如何自动执行留待预发布完成后讨论。

### 选择测试的原则

- 每项适用接受条件必须有验证去向，但不要求每条条件都同时写三层测试。
- 分支与输入组合优先使用快速、定位明确的测试；关键组件连接使用集成检查；关键用户旅程使用适量E2E。
- 新用户流程或重要行为变化：先写可执行的关键E2E/验收测试，并在前提就绪时确认预期失败；内部用单元/集成红绿循环实现；最后同一外层测试通过。
- 局部算法、DTO或后端修复：先写对应层的失败测试；合并前仍选择相关关键流程E2E验证。是否新增用例取决于已有覆盖，不能用“不新增E2E”解释为“不执行E2E”；入口按实际链路选择，不强造浏览器步骤。
- 已有行为本来正确时，已有测试可以直接通过；记录为基线/回归证据，不伪称新TDD红灯，不故意破坏正确实现。
- 纯文档按根规则检查差异和引用，无需站点E2E；软件改动不因未新增可观察逻辑就豁免合并前相关E2E，也不为凑数量新增无价值用例。
- 共享修改增加受影响消费者有限回归；批准专项最低要求保持。测试金字塔不是固定比例，不用测试数量代替覆盖判断。
- 真正外部提交、真实收件验证单列条件与授权。模拟到provider边界的浏览器流程不能升级为真实收件证明。

## 6. TDD的执行证据

每个需要TDD的新增/修复行为保持以下链条，相关日志可集中保存：

1. 引用批准接受条件或明确技术要求，独立确定预期结果。
2. 写能抓住该错误的测试；指出错误分支、遗漏副作用或合同破坏是什么。
3. 运行并读结果：因目标行为缺失/错误失败才是有效红灯；语法、导入、服务未启动属于测试/环境问题。
4. 最小实现并运行同一测试，确认变绿；运行与改动直接相关的回归。
5. 需要时重构并保持相关检查通过；最后确认外层用户流程及适用视觉状态。

任务记录保存测试路径/用例、执行命令、红灯原因与实现前版本、绿灯版本和结果。已有日志可直接引用，不要求每个循环生成新报告，也不要求每个红绿步骤各自commit。

测试预期不调用被测逻辑生成；不以源码字符串存在、mock元素存在、无行为的常量检查充当业务证明。只替换确需隔离的外部/慢依赖；参数、调用次数和顺序属于真实合同的，可以检查。模拟结构应符合真实合同，不能为了方便吞掉被测行为依赖的副作用。

缺少TDD历史只能如实标为后补回归，不能倒写执行顺序。原有代码与其他任务修改必须保留。重构和例外依当前授权与上位规则处理，不借Skill措辞删除既有成果。

## 7. 技术审查怎样检查测试充分性

独立技术审查沿用同一接受条件与差异范围，检查：

- 条件是否遗漏；测试层次是否覆盖真正风险；关键链路是否只剩mock。
- 断言是否观察真实结果；预期是否独立；错误分支、参数、缺失状态改变是否会触发失败。
- 测试/运行环境是否真的对应被审网站、版本、数据；有无跳过、未运行或采集无效的检查。
- 共享消费者回归是否足够；外部依赖和未测范围是否准确。

优先复用同一版本的有效执行证据，不默认重跑同一套命令。发现具体风险、证据缺口或反证时定向检查。审查者无法从差异验证的跨任务条件交主控核对，不能直接写通过。适用独立实际验收要求仍由原流程执行。

SDD的返修上限与裁定不能豁免批准条件：真实缺陷可按规则明确延期或形成部分交付，但不因此宣称全部符合、独立验收通过或可发布。裁定与风险进入主回执，不能只留在随后清理的临时台账。

## 8. 派工、并发与恢复

实施/审查派工至少明确：本任务ID、网站、批准条件、读写范围、BASE/HEAD或差异基线、消费/产出接口、环境、测试边界、已有授权、报告位置与停止点。使用既有计划/任务brief路径，避免复制全部聊天记录。

- SDD按当前技能组织实施与任务审查；实施者不自行再派重复审查者。
- 并行只用于相互独立且无写入/状态冲突的工作；多个角色名称不构成并发依据。
- 多页面批次继续逐页实施、验证与提交；共享实现先稳定，后续页面验证消费结果。develop与main按开发交付流程第6节串行集成。
- worktree只解决部分代码隔离；CMS、端口、Build目录、测试输出与进程归属仍需核对。测试文件若硬编码历史证据输出目录，先解决输出隔离，不得直接覆盖已冻结证据。
- 长任务记录已完成任务、commit、当前修复轮次和决定；恢复时结合台账与Git确认，不重复派发已完成工作。
- 实施报告至少返回完成范围、代码身份、测试命令/结果、证据、未决项；主控核对实际差异与证据后综合，不直接转抄PASS。

## 10. 两套本地环境

开发环境用于频繁修改、调试和验证；预发布环境用于集成后的稳定候选验证。两者必须能相互独立运行、停止和恢复。预发布初始只覆盖`tio2-my`，其他网站采用此模式时另定其身份与资源。

| 维度 | 本地开发环境 | 本地预发布环境 |
|---|---|---|
| 源码 | 从develop创建的任务分支/worktree；允许记录清楚的未提交修改 | 精确、干净的本地main commit，经git archive冻结 |
| Next.js模式 | next dev用于开发；需要时在任务独立目录build/start验证 | 冻结源码执行生产模式build/start，禁止用next dev充当候选 |
| 网站端口 | 按任务分配未占用端口并记录；现有多站脚本是3001/3002/3003，不能当作单站默认启动器 | 127.0.0.1:3100 |
| CMS | 现有开发WordPress在127.0.0.1:8080；共享数据变更串行或另行隔离 | 独立WordPress在127.0.0.1:8180 |
| 数据/上传 | 开发栈自己的volume和夹具；共享消费者要明确 | 专用prerelease_db/prerelease_wp volume，不能共用开发库或uploads |
| 配置 | 任务/开发栈自己的忽略文件，不输出值 | 根目录.env.prerelease.local，按预发布配置示例填写 |
| Build/证据 | 每任务独立Build目录、端口和输出 | 每run独立冻结源码、Build ID、CMS身份、run Manifest与证据目录 |
| 测试目的 | TDD、局部集成、关键E2E、页面交付自检 | 集成后的目标全站候选、跨页关系、环境差异和发布前准备 |
| 变更方式 | 原范围内编辑并定向验证 | 不直接改候选；回开发修复、验证、按授权集成，再生成新run |
| 外部副作用 | 优先模拟；真实动作依适用授权 | 普通预发布测试禁止真实表单发送；单独实发入口依明确授权 |

环境入口：[开发Compose](../wordpress/docker-compose.yml)、[预发布Compose](../ops/prerelease/docker-compose.yml)、[预发布使用说明](prerelease-environment.md)。预发布的具体端口、volume、seed和命令合同以该说明及当前实现为准，不在本文件复制另一套配置。

开发中的临时页面验收runtime仍可按原合同保持；它属于开发/候选验证用途，不替代集成后预发布。不能为了更新预发布停止其他任务仍需保持的验收runtime。

develop组合验证在开发环境完成：在隔离工作区检出待晋级的精确develop commit，记录网站、开发CMS/夹具版本、配置、独立端口、Build目录和测试输出。按测试需要构建并启动该候选，核对实际服务身份后执行集成回归和E2E；CMS写入遵守原授权与恢复要求。保存命令、结果、证据和恢复记录，不覆盖其他任务的运行或证据。它不是预发布，不调用仅接受main的预发布启动入口；候选变化后按影响复验。

## 11. CI/CD如何接入

讨论状态：用户已明确待本地预发布完成后再讨论CI/CD具体做法。本节保留候选流程供后续讨论；分支门槛、E2E和main预发布规则已经生效，自动触发、平台选型、统一门禁与晋级编排尚不在本次实施范围内。下表不表示自动化已实现或获准启动。

CI（持续集成）负责让变更在进入develop及从develop晋级main时接受可重复检查；CD在本地负责把满足条件的main交付到预发布并保留可验证候选。本项目此处采用持续交付：生产部署仍是独立授权动作，不默认自动部署生产。

目标执行链如下，箭头不产生新操作授权：

```text
批准需求 / 技术合同
  → 从develop创建codex/<task>：TDD + 定向单元/集成 + 关键E2E通过 + 技术审查
  → 原流程要求的页面交付与独立验收
  → 集成前CI检查与准确基线核对
  → 获授权串行合入develop
  → develop精确候选的集成回归与E2E通过
  → 获授权由develop合入main，核对合并结果与已测组合一致
  → 干净main冻结源码 + 独立预发布CMS + 生产模式构建
  → 预发布运行身份/健康 + 冒烟 + 本批次适用全站验收
  → 保持该候选和证据；生产发布准备按原流程处理
```

不把本地预发布通过倒置为当前页面入队的前提；它验证集成结果。页面级验收与集成后的预发布验收对应不同对象，分支路线统一按开发交付流程第6节执行。

| 阶段 | 触发与责任 | 检查/动作 | 失败处理 |
|---|---|---|---|
| 开发反馈 | 实施者每次行为改动 | 最小相关测试；需要时检查类型、接口、关键用户流程 | 原任务系统调试，不带失败推进 |
| 集成前CI | 主控准备集成候选时 | 固定BASE/HEAD、批准与审查身份；依影响面选lint、typecheck、单元/集成、目标build及关键E2E；记录前提和跳过项 | 未运行不能当PASS；前提失败阻止受影响环节 |
| develop组合CI | 任务通过E2E及适用验收、获授权合入develop后 | 对精确develop候选执行集成回归与E2E，覆盖本批次跨页和共享影响，绑定HEAD | 失败或未验证不晋级main，记录阻断及修复责任 |
| main晋级CI | develop组合检查通过、获授权合入main时 | 合并前核对最新main与待合组合；合并后核对代码树及证据一致，变化部分补验 | 未通过不推进预发布；仅合入develop不标记INTEGRATED_LOCAL_MAIN |
| 本地CD构建 | 已就绪main候选，由主控/集成任务调用现有入口 | 核对干净main、锁和端口；冻结源码、核验seed、构建并启动专用栈 | 保存failedStage及日志，不自动删库或误停开发栈 |
| 预发布验证 | 构建成功且身份成立后 | 先检查健康/版本，再运行冒烟和本批次适用验收；核对证据本身 | 不晋级；回开发修复或定位环境，生成新候选后复验 |
| 候选保持/更新 | 主控维护 | 保留run、commit、Build、CMS和测试证据；main移动后按STALE_MAIN解释 | 不把旧Build挂到新main；新版本另构建、测试和记录 |

检查分组应有完整执行命令、工作目录、环境/网站、测试清单、超时/失败判据和证据位置。文档变化只做文档检查；代码变化按依赖分析选择，不用无差别全仓测试充当CI。现有`npm run validate`会运行较宽范围，不能默认等同任何单页CI合同。`verify:root-only`继续要求专门授权。

CI/CD检查命令返回0还不够：应核对机器状态、预期测试是否实际执行、用例跳过情况和完整结果。环境HEALTHY只说明身份/健康成立，不等于预发布验收PASS。

同一代码和环境的有效检查可有依据复用：集成前检查引用开发结果，组合后按差异增加必要回归，不把表中的阶段理解为必须原样重复全套测试。清楚记录检查来自哪个对象；源码、数据、依赖、配置或测试变化使结论失效时，仅重跑受影响条件。失败重试先定位原因，首次失败记录保留，不能通过重复运行直到偶然绿灯来关闭问题。

## 12. 现有能力与自动化缺口

截至本次源码核对：已存在Vitest/Playwright入口、开发Compose、预发布Compose与`scripts/prerelease.ps1`。尚未发现仓库`.github/workflows`；本次没有核查外部CI平台，不据此推断平台配置状态。

| 能力 | 当前已具备 | 当前边界/后续工作 |
|---|---|---|
| 开发环境 | 原开发CMS栈及任务开发/测试入口 | 按任务记录端口、Build、数据和授权，不能自动套用多站启动脚本 |
| 预发布交付 | prerelease:start/status/stop/reset/test及独立真实表单入口 | 由操作者/Agent显式调用，不等于提交后自动流水线 |
| 固定候选 | 干净main、冻结源码、Build/CMS/run身份、专用栈与操作锁 | 当前干净工作树约束阻止把未提交流程修改混入候选；不能为启动而自动提交其他工作 |
| 预发布冒烟 | prerelease:test运行prerelease-smoke.spec.ts，拦截非GET请求 | 代表页面和共享能力的冒烟，不证明完整全站合同已覆盖；按本批次补充适用验收矩阵 |
| 测试源码身份 | Test动作在调用仓库目录运行Playwright | 记录测试代码的commit/差异；要求严格复现时使用匹配候选的测试源码，不假设已从冻结源码运行 |
| CI自动编排 | 独立检查命令可被调用 | 变更范围选择、统一结果汇总、触发器与门禁编排尚未因本次文档修订实现 |
| CD自动晋级 | 预发布启动/构建已有编排 | 集成检查通过后自动触发、并发队列及统一流水线回执尚需实现与试跑；此刻按上述合同显式执行 |

从干净main准备预发布时，按[使用说明](prerelease-environment.md)调用现有命令。`start`包含CMS初始化/受控seed和构建，不是只读检查；`status`包含专用临时WP-CLI身份核验，也不等于简单查看端口。普通CD不调用`reset`或`test:forms-live`。真实提交需已有明确授权，配置开关本身不授予权限。

当前预发布smoke有意拦截所有非GET请求。需要验证包含POST的应用内部链路时，不能用该smoke结果代替集成验证；使用有明确边界与外部发送防护的适用测试。

## 13. 制品、数据与恢复

- 开发Build不直接搬入预发布；预发布用精确main和预发布配置构建。预发布测试和运行必须使用同一候选Build。
- 保存源码commit/archive hash、锁文件/依赖依据、镜像身份、Build ID、CMS/seed/config身份（脱敏）、测试源码版本、命令、结果及run ID。
- 开发数据库不直接覆盖预发布；经版本化的seed/迁移合同进入候选，核对目标scope及恢复要求。已有预发布数据正常停止后保留。
- 旧源码快照不包含完整数据库回退能力。数据或seed已变化时，回退必须同时考虑兼容源码、数据备份/恢复与配置，不能只启动旧Build宣称恢复完成。
- 现有`start`只接受当前干净main，不能假定已有任意旧run的一键回滚入口。失败优先保留证据、从develop建立修复任务分支，经过任务E2E、develop组合回归/E2E和授权合并形成新main候选再构建；需撤销main或恢复数据时按具体授权处理。
- 更新预发布可能涉及停止现有预发布实例并重建，不宣称零停机或原子切换。先记录被替换候选及保留证据，不干扰页面验收runtime。
- 生产配置可能影响构建输出，预发布Build不能无条件直接晋级生产；未来生产CD需确定制品策略、生产配置、迁移、回退与部署后验证。本轮不配置生产流水线。
