# MY 本次路由数据修复

本程序仅承接已核实的 95 项路由差异：27 条记录新增 81 个路由字段，14 条产品记录更新发布状态。不是通用内容导入器，不安装 `content-only` 能力，也不修改旧 PREPARED 事务。

## 包与执行

`ops/production/build_route_repair_bundle.py` 从准确 Git 提交生成独立管理员包。输入为只读生产演算报告整理的 `d16-my-route-repair-v1` payload；目标逐项匹配已批准的 41 条 CMS 路由，原值摘要和前后 v2 内容摘要均绑定包。程序只有三个可写 metadata key，保留正文、JSON 配置、其他 metadata 和旧 slug。

管理员核对外层哈希后解包到固定 `/root/d16-route-repair`。`admin/root-route-repair.sh` 清空环境并使用隔离 Python 运行：

- `plan`：验证运行身份和现状，保存唯一计划。首次在数据库容器 `/run` 创建 root 私有客户端凭据文件，不打印秘密；不更新 CMS。
- `apply <planSha256>`：持有新旧发布锁，验证旧发布状态未变，暂停共享数据库写入，备份全库并在隔离容器恢复验证，再在单个 SQL 事务执行变更；验证 v2 内容摘要及所有路由目标。
- `status`：读取当前修复阶段。
- `rollback <planSha256>`：仅在本次写入仍关闭时恢复本次整库备份；已开放写入后拒绝历史恢复。
- `finish-opening <planSha256>`：开放写入过程中断时，仅续接开放，不重做数据库更新。

生产入口要求 root 保护文件，并绑定实际数据库主机、库名、WordPress 表前缀、非特权 WordPress 账户和原前台容器/镜像。旧发布状态文件仅比较，不改写。所有正常写入均由现有 `InstallationDatabase` 暂停；root 管理员仍属于可信运维边界。

## 缓存与验证边界

沿用原前台签名重验证接口发送 `paths:[]` 的站点通知，核对事件 ID、网站标签和空路径回执。请求及 41 个兼容性页面检查直接在已绑定容器内运行。原接口为 `revalidateTag(...,'max')`，这是延迟失效，不能声称已同步完成所有用户页面刷新；也不重启容器冒充清除磁盘缓存。

本次回执证明数据库达到目标且旧前台兼容性冒烟通过。后续仍需执行正式前台发布及全站验收，不能将管理员修复完成当作整站发布完成。

## 本地验证

`tests/production-runtime/route_repair_rehearsal.py --payload <payload.json>` 只读导出本地预发布库，克隆到有独立身份的数据库和只读 WordPress 文件系统中。验证真实 95 项 SQL 更新、先备份后隔离恢复校验、写入后验证失败的整库恢复、禁止历史恢复和测试资源清理。HTTP/缓存回调在该数据库演练中是夹具，另行测试真实前台签名通知，不能混报。

生产运行前重新 plan；任何基线变化会拒绝 apply。数据库演算报告不是正式备份，也不是发布完成回执。
