## 1. 分工

| 责任方 | 负责内容 | 交接结果 |
|---|---|---|
| 每个网站的策划项目 | 网站定位、研究、页面职责、文案、视觉、业务事实、批准版本与独立验收 | 一个可定位的当前批准交付入口、验收依据及依赖 |
| D16 | 技术承接、架构与实现、CMS集成、测试、缺陷修复、部署及发布操作 | 实现版本、技术验证回执；获授权后提供部署及回退记录 |
| 用户 | 业务与范围决定、适用的阶段批准、发布及其他需授权操作 | 明确对象和范围的决定，复用已有记录 |

D16可以指出内容或设计冲突并提出具体修改建议；不自行改写策划批准源。策划侧可以验收实际网站并提出问题；技术修改由D16完成。跨工作区状态回写只在明确任务范围内进行，普通开发回执留在D16即可。

## 2. 承接：复用一份交付入口

一次任务可覆盖一个页面、一个模板、一个共享功能或明确的一批页面。已有交付包和批准记录满足以下信息时，直接引用，不另做同内容的审批表：

| 必要信息 | 应能回答的问题 |
|---|---|
| 身份与范围 | 哪个网站、语言、页面ID/URL或共享功能？哪些消费者受影响？ |
| 批准基线与授权 | 当前Manifest/交付入口在哪里？采用什么版本或哈希？用户授权了哪些实现动作？ |
| 实现输入 | 文案、结构、完整视觉、响应式及交互状态、媒体、字段、SEO与共享合同在哪里？按任务选用，不要求技术修复重新提交全套策划 |
| 依赖与变化 | 哪些路由、内容、表单或外部配置已就绪？哪些仍待确认？相对当前代码改了什么？ |
| 验收与环境 | 按什么标准验收？在什么环境验证？由谁承接策划侧验收？ |

已批准的正文和视觉可保留原文件，只在D16记录来源版本及运行需要的资产/数据。生产运行不能依赖`D:\23MySec`、`D:\11SEO`等本机路径。

遇到缺项时先说明具体影响，继续不受影响部分。只暂停依赖缺失身份、冲突批准或必要配置的动作。未知事实不自动变成零、否或禁用；由对应策划来源或用户解决。

接单时先比较本任务涉及的现有共享组件与批准输入，特别是完整页面中的菜单、Footer、Cookie、表单和适用交互状态。“已存在共享实现”不等于“已符合本次批准版本”。一致项引用依据；差异项说明授权内修复或需要哪个具体决定。与此同时定位接收项目/任务、交付方式和可用发送能力；这些记录不增加新的批准关卡。

## 3. 实现：在范围内自主处理技术问题

1. 读取当前代码、Git状态、相关规则和已有实现；确定网站及共享依赖，保留其他任务修改。写Next.js代码前按根规则读取本地对应版本指南。
2. 根据任务复杂度使用适用的Superpowers设计、计划、实现、调试与审查方法；已有有效设计和批准直接复用。技能无法找到时说明实际限制；必要方法缺失时只暂停依赖步骤，不冒充技能执行。
3. 原范围内决定组件拆分、数据校验、缓存、错误处理和测试实现；只有改变批准内容、页面身份、视觉/业务行为或授权范围时，才提出具体决定项。
4. 本地CMS写入使用现有受限、可核对、可恢复的导入/seed流程。任务需包含相应数据变更；既有授权有效时不重复确认。不得借修复单页执行全库迁移或影响其他站。
5. 实现和测试发现的缺陷在当次范围内修复；外部依赖单独记录其影响和负责人，不用临时假数据伪装完成。

共享组件按现有所有者维护，单页消费共享实现，避免复制Header/Footer等产生分叉。新增网站的技术隔离方式按需求决定，不把当前共享WordPress和Next.js组合固定成永久架构。

### 日常执行顺序

| 步骤 | 应留下的结果 | 进入下一步的条件 |
|---|---|---|
| 接单核对 | 身份、批准组合、共享差异、依赖及环境 | 目标明确；缺口已定位其影响，可并行处理不受影响部分 |
| 实施与测试安排 | 验收条件→实施位置→检查方式的对应关系 | 知道每项适用条件如何证明，不只列命令或测试数量 |
| 开发与局部验证 | 当前改动及相关正常/失败状态结果 | 实现和相关检查成立，问题在原范围内修复 |
| 完整页面自检 | 实际运行、适用画面/交互与影响面回归，证据目视核对 | 可交付范围的实现问题已解决，未测和外部依赖如实登记 |
| 审查与版本固定 | 适用代码审查、实际预览身份、主回执及证据索引 | 结论可追溯到准确代码/数据/运行组合 |
| 交回与反馈处理 | 送达依据、接单或验收结果、问题逐项处理 | 独立接收或有明确下一动作；接受后停止重复返修 |

简单任务可以合并记录，步骤不机械增加文档、全量测试或人工审批。D16负责目录、构建、测试及证据组织；仅在工具或必要环境确实不能自行处理时请求用户操作。请求前完成准备，给出含工作目录、网站、构建目录和端口的完整操作，复用已有授权；用户操作后核验实际服务身份，不能只依据“Ready”判断运行了目标版本。本流程不表示已提供新的启动自动化工具。

## 4. 验证：与变化和影响相匹配

| 变化 | 适用验证 |
|---|---|
| 规则或说明文档 | 差异、引用路径、职责及授权一致性；无需网站构建 |
| 单页/模板/交互 | 对应单元或集成测试；必要的目标站构建、合同断点及关键交互E2E |
| CMS、路由、缓存、SEO或表单 | 对应契约和集成检查、网站隔离、相关失败状态；必要时用受控本地运行验证 |
| 多站共享代码 | 上述相关检查，加受影响消费者的有限回归；有实际需要才增加多站构建 |
| 发布 | 当次环境和变更要求的验收、构建、配置、依赖及部署后检查，不照搬旧站全量命令 |

按实际执行报告版本、环境和日期。清楚区分源码检查、静态截图、模拟接口、本地CMS运行、服务商接受与实际收件。未执行的检查或未覆盖环境明确写出。

### 交付前检查证据本身

- 每条适用验收条件记录检查方式、版本/环境、结果和原始证据；不适用或未验证说明原因。正常开发选择与改动和共享影响面相关的检查，不把Poland三站/六异常矩阵变成每个页面必跑清单。
- 作为交付依据的适用截图需实际打开查看，确认画面完整、文字可读、状态正确，无空白、截断或错版；自动尺寸/像素检查用于辅助。键盘焦点需有可感知的状态变化，仅DOM焦点、CSS色值或axe无违规不足以证明。
- 区分响应式视口、浏览器原生缩放和真机。合同要求实际缩放时使用对应方法并核对画面；工具产生错误截图时先区分采集和页面故障，保留反证，不修改图片伪造通过。
- 实际预览应绑定commit或精确未提交快照、构建身份、相关CMS/配置状态和检查时间。重建后复验受影响条件；继承旧结果需说明源码、环境和影响面依据，不把旧图挂到新Build。
- 有临时CMS或缓存操作时核验恢复。正式证据保存在任务目录；已弃用采集入口注明替代入口，后续运行不得覆盖已冻结历史。发现旧结论不受证据支持时保留原件并在当前入口明确纠正。

`verify:local`、`sites:start`等现有脚本可能覆盖多个站点或带有本地数据操作；先读当前脚本范围，不因名字包含local/verify就把它当作单页只读检查。`verify:root-only`继续遵守根文件的专门授权限制。

## 5. 回执与独立验收

沿用`docs/verification/`已有对应页面或功能位置；新网站使用`docs/verification/<site-id>/<task-id>/`避免重名。已有路径不批量迁移。一次任务用一份主回执链接详细证据即可，不为每个状态新增一套报告。

主回执的最小内容：

```text
网站 / 页面或功能 / 任务范围：
策划交付入口 / 精确批准基线：
代码位置 / branch / commit或未提交差异基线：
本次实现及相对批准源的差异：
测试环境 / 日期 / 结果 / 证据路径：
预览入口及对应运行版本（适用时）：
Gate8 Evidence Manifest路径 / evidence HEAD / runtime保持条件（D23任务适用时）：
未决项 / 影响 / 下一责任方：
技术完成状态 / 策划验收记录引用 / 发布授权与实际部署状态：
RECHECK_SCOPE_STATUS / PAGE_GATE9_STATUS / INTEGRATION_STATUS / RELEASE_STATUS（D23任务适用时）：
交付目标 / 送达方式与依据 / 接单或验收反馈：
```

开发回执不自行标记策划Gate通过。独立验收退回时，按具体问题定向修复并复验受影响范围，返回修复版本。修复或源内容变化使旧证据失效时注明范围；不反复复验未变且身份可核对的成果。

页面状态分维度保存：策划批准、技术实现、验证、独立验收、发布授权、实际部署。某维度缺记录就是未核实，不从另一个维度推断。无需重新编一套与策划侧竞争的页面总表。

### 送达与停止条件

材料已准备、文件面板已排队、消息已送达、对方已接单和验收已通过分别记录。成功发送需有准确接收目标及工具或人工确认；发送成功仍不等于接单。工具不可用时提供完整主回执和可用交付方式，明确尚未发送，不以打开文件或排入面板冒充通知成功。对外消息继续遵守适用授权，不增加重复内容批准。

问题分为实现缺陷、证据缺口、跨页开发依赖、外部账户/收件条件、发布条件；每项说明已证明部分、仍缺材料、影响及下一责任方。随着补证缩小未决范围，不能反复把已验证本地接线列为缺失。未能定位具体负责人时写明责任角色和待定位事实，不虚构已派发。

指定版本的实现问题被独立接收后，保存接收记录并停止重复返修及无关测试。只有新反证、代码/内容/环境变化或明确新任务触发对应范围的工作。Gate整体因外部依赖未关闭时，不自动把页面重新标记为代码待修；已关闭问题遇到具体新反证也不能拒绝处理。

## 6. D23 Gate8机器交回与本地main串行集成

### Gate8机器交回

D23任务的Gate8首次交回及每次返修交回都在任务证据目录生成`gate8_evidence_manifest.json`，并通过D23当前Schema验证。Manifest至少绑定交接与任务ID、`site_scope`、Page ID和接受条件ID、repository/branch/baseline/implementation/evidence HEAD、工作树检查时间、Build目录与Build ID、runtime身份及路径检查、证据路径与SHA-256、人工回执和已知开放项。证据使用仓库相对路径并进入指定evidence HEAD；工作树字节因Git换行过滤与commit blob不同的，分别记录SHA-256和blob ID。

Gate6交付内的代码或片段按`APPROVED_CONTRACT`、`REFERENCE_IMPLEMENTATION`或`PROTOTYPE_ONLY`接收；未标身份的代码按`PROTOTYPE_ONLY`处理。技术实现可以替换参考实现，但不得改变已批准合同的结果。

人工主回执中每份验收证据各写一行`EVIDENCE: <repo-relative-path>`，这些路径的集合必须与Manifest的`receipt_evidence_references`完全一致。交回时runtime的`hold_until`为`GATE9_PASS_OR_RETURN_NOTICE`；保持同一候选，直到Gate9向原Gate8任务发出通过、返修/补证或明确释放通知。运行身份必须更换时，先交回新的implementation、evidence、Build和runtime身份及差异；无法保持时如实标记受影响条件为环境失败或未验证。

Gate9返回分别记录`RECHECK_SCOPE_STATUS`、`PAGE_GATE9_STATUS`、`INTEGRATION_STATUS`和`RELEASE_STATUS`。局部复验通过、页面Gate9通过、进入集成队列和发布授权是四个不同事实；`INTEGRATION_READY`只表示具备进入本地`main`队列的资格，不等于已合并，也不授予合并权限。

### 本地main唯一串行队列

1. 同一时间只由一个D16集成任务更新本地`main`；开始前确认没有其他集成任务处于`INTEGRATING`。
2. 集成前重新读取本地`main` HEAD和工作树状态、目标分支HEAD，以及Gate9接受的implementation、evidence HEAD和Build身份。目标分支在验收后发生实质代码变化时，原`INTEGRATION_READY`失效，按差异影响重新复验。
3. 只有当前用户指令或已有明确授权覆盖本地合并时才执行。合并冲突涉及批准语义时返回原实现owner；集成任务不静默改写批准内容或行为。
4. 合并后记录`main`前后commit、合入对象、冲突处理和受影响批次的组合回归。组合回归失败时使用`CONFLICT_RETURNED`或`INTEGRATION_BLOCKED`，不能把单页旧PASS扩张为`main`通过。
5. `INTEGRATION_STATUS`使用`NOT_READY / INTEGRATION_READY / QUEUED / INTEGRATING / INTEGRATED_LOCAL_MAIN / INTEGRATION_BLOCKED / CONFLICT_RETURNED`之一，并在当前任务入口保存依据。

本地`main`集成不授权Git push、Preview或Production部署、生产WordPress写入、DNS、sitemap、索引或发布。对应操作继续按第7节取得和复用准确范围的授权。

## 7. 发布：D16执行，授权按网站和环境限定

发布任务至少明确网站、目标环境、待部署代码/内容版本、适用验收、发布范围、回退方式和部署后验证。配置或交付仍有缺项时，先完成可核查的发布准备再提交具体待决定项。

- Preview部署、Production部署、远程CMS写入、Git push、DNS、迁移和索引按各自已有授权范围执行。一次明确授权可以覆盖列明的多项操作，不要求机械拆成多次确认。
- 网站内容可对外使用，不等于已授权部署；部署成功也不等于允许索引。授权与执行结果分别记录。
- 核对网站绑定、环境配置、CMS/媒体可达性、表单路由与数据流、相关跨页依赖。只检查本次网站和发布范围需要的项目。
- 记录实际部署ID/版本、URL、时间、验证结果及回退定位；真实对外表单提交需相应授权，模拟结果不能宣称收件成功。
- 发布失败时按已授权的回退方案处理；回退超出既定范围时提出具体影响与所需决定。不能以“发布归D16”推导无限生产权限。

## 8. D23实例与历史兼容

D23两个交接点的逐项输入、输出、接收检查和缺项处理见[Gate 6→8 / Gate 8→9详细清单](d23-gate-handoff.md)。这份清单补充本流程，不新增审批或要求其他网站采用同一Gate编号。

D23阶段按其当前生效入口解释；2026-09-07由D23项目索引核对为[工作流V3.2](D:/23MySec/docs/architecture/GATE_WORKFLOW_V3.2.md)：Gate 0–4完成策划内容与完整视觉，Gate 6总审交付，Gate 8由D16技术承接，Gate 9由策划侧独立只读验收，Gate 10是单独发布授权。后续通过策划当前索引定位，不按文件名最大版本猜测，也不把D23内部阶段关闭机制转成D16开发或发布权限。

旧Gate 5职责已并入4、旧Gate 7职责已并入6。既有交付包、文件名、哈希和批准不重命名、不重新审批；承接时引用原组合并说明对应关系。阶段合并不扩大原页面授权、不恢复暂停任务。

D23的Gate编号仅用于D23。D11及未来网站可以使用自己的策划流程，只需提供第2节所述交付信息，并明确其独立验收与发布授权。

本文件替代历史规格中“正常开发只面向Site A”等与当前多网站定位冲突的治理描述；历史业务事实、页面批准、冻结状态及证据保持其原范围。原README的双站操作说明属于历史参考，使用前核对当前脚本与任务。
