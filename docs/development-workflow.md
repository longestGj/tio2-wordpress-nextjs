# D16 开发交付流程

本文件只规定批准输入进入 D16 后，如何形成可审查实现并合入 `develop`。生产候选、`main`、预发布、打包和生产验收由独立的[发布流程](release-workflow.md)负责；开发完成不会自动启动发布。

## 0. 按任务阅读与文档职责

开始任务先读根 `AGENTS.md`、[网站登记](site-registry.md)、[软件架构](software-architecture.md)和本网站的有效批准入口。开发方法与本地环境见[内部开发与测试执行](development-execution.md)，输入与交回清单见[通用开发交接](development-handoff.md)。

每项任务用[通用开发任务模板](templates/development-task.md)或已存在的等价主记录固定本次事实。D23 任务可以继续使用其专属模板和 Evidence Manifest，但专属字段不改变本文件规定的开发边界。

规则文件保存职责和停止条件，任务记录保存本次网站、批准版本、代码身份、命令、结果和未决项。历史回执不证明当前候选通过。

## 1. 职责与终点

| 角色 | 职责 | 不据此产生的事实 |
|---|---|---|
| 策划或用户 | 批准业务事实、文案、URL、视觉、行为和接受条件 | 不决定 D16 内部实现细节 |
| Gate8 | 接单、设计、TDD 实现、相关测试、实际页面自检、调用独立代码复审、返修、准确合入 `develop`、写开发回执 | 不生成发布候选，不操作 `main`，不连接生产 |
| 独立代码复审者 | 对冻结的 BASE/HEAD、测试和影响面给出通过或可执行问题 | 不改业务代码，不合并分支，不授予发布动作 |
| 发布负责人 | 只在收到独立发布指令后消费 Git 中的开发回执和实际差异 | 见[发布流程](release-workflow.md) |

开发终点是：Gate8 已把独立复审通过的准确实现合入 `develop`，重新核对合并结果，并写出状态为 `MERGED_TO_DEVELOP` 的[开发回执](templates/development-receipt.md)。

## 2. 接单与范围固定

Gate8 在写代码前记录：

- 任务 ID、网站 ID、页面/共享功能、语言与目标路径；
- 当前批准入口、版本或哈希，以及替代关系；
- 接受条件、视觉状态、数据与内容身份、共享消费者；
- 目标开发环境、测试边界、已有授权和本次终点；
- `develop` 基线、任务分支、允许修改的路径和已存在的用户改动；
- 缺失输入、外部依赖、责任方，以及它们阻止的具体步骤。

可从有效资料与既有授权确定的事项直接复用。缺口只阻止依赖它的步骤，例如缺少真实邮箱确认不阻止无外发的页面开发。业务事实冲突返回原批准方，技术缺陷由 Gate8 在原范围修复。

共享代码修改前列出消费者；网站身份、CMS scope、缓存、SEO、表单和媒体必须绑定准确站点，禁止跨站 fallback。Site B 冻结和 Site A 导航限制继续按根规则执行。

## 3. Gate8 开发与验证

开发从当前 `develop` 创建 `codex/<task>` 分支或隔离 worktree。保留工作区中的其他改动，不直接在共享分支开发。

Gate8 按任务风险执行：

1. 将接受条件映射到代码入口、测试层次和可观察结果。
2. 对新增或修复行为先写测试并确认因目标行为缺失而失败。
3. 写最小实现使同一测试通过，再运行受影响的单元、集成和关键任务 E2E。
4. 对视觉或交互交付实际查看适用视口和状态；对数据、CMS、缓存、SEO、媒体和表单核对真实边界。
5. 保存准确命令、版本、环境、结果、跳过项和原始证据。模拟提交、服务商接受和实际收件分开记录。

纯文档变化检查链接、差异与规则一致性即可。共享修改增加受影响消费者的有限回归。测试数量、DOM 断言或环境 `HEALTHY` 都不能替代接受条件和实际页面证据。

涉及 CMS、前端、配置或构建的任务按[职责划分](superpowers/specs/2026-09-13-cms-frontend-build-responsibilities-design.md)检查边界：先分类内容、稳定身份、技术结构、动作、政策和审批证据，再确定实现与兼容范围。内容读取不以历史文案相等作为技术有效条件；正文与可编辑 SEO 使用同一 CMS 来源；配置标明生效阶段；缓存生产者与消费者按准确网站共用身份约定。

解耦任务须同时验证合法内容变化可生效、非法技术输入仍被拒绝，以及实际 CMS 到正文/SEO/交互的链路。刷新接收、缓存失效、页面新版本分别观察；普通与敏感更新的时效和失败条件在批次中固定。构建成功不代替内容批准，方案获批不代替实现完成或发布指令。

## 4. Gate8 调用独立代码复审

Gate8 在任务实现和相关验证稳定后，冻结准确的 BASE/HEAD、工作树状态、批准条件、变更路径、测试证据和已知开放项，调用与实施分离的代码复审。复审只读核对：

- 实现是否符合批准范围和当前软件架构；
- 测试是否能观察真实行为，红绿证据是否可信；
- 共享消费者、网站隔离、失败路径和恢复边界是否遗漏；
- 源码、运行、Build、CMS 和证据身份是否一致；
- 跳过、外部依赖和未决项是否被准确报告。

复审发现代码或测试缺陷时，Gate8 在原任务分支返修，运行针对性红绿循环和影响回归，再以新的准确 HEAD 请求复审。批准内容冲突返回原决定方。没有独立复审通过结论，不得合入 `develop`。

## 5. 准确合入 `develop`

同一时间由一个 Gate8 集成任务更新 `develop`。合并前重新读取 `develop` HEAD、来源 HEAD、工作树和复审对象；如果来源变化，旧复审结论只对未变化部分有效。

合并后 Gate8：

1. 记录合并前后 commit，并确认实际树包含获批的准确实现；
2. 按合并差异运行必要的集成回归或关键 E2E；
3. 确认没有混入其他网站内容、密钥、临时证据或未批准路径；
4. 在 Git 中写开发回执，状态只能在上述条件成立后设为 `MERGED_TO_DEVELOP`。

开发回执至少包含任务、主体、合并 commit、改动路径、已运行测试、受影响消费者、预计发布影响和未决项。它不等于预发布通过、已打包或已部署。

## 6. 交回、退回与停止条件

交回分别记录材料准备、送达、接收和复审结论。文件存在或面板排队不代表已送达。候选变化时提供新的源码与运行身份，旧证据保留并注明被替代。

退回项至少给出原条件或问题 ID、复现版本、环境、现象、预期、证据和责任方。Gate8 回复根因、最小改动、新 HEAD、定向复测和共享影响。无新反证时停止重复返修。

当 `MERGED_TO_DEVELOP` 回执已经进入 Git，开发任务结束。后续工作若被要求，由发布负责人从一条独立发布指令开始；开发任务本身不隐含任何远程写入或环境变更。

## 7. 发布：独立指令入口

发布只从一条限定主体、目标环境、允许动作和本次终点的独立发布指令开始。开发回执、合入 `develop`、内容批准或历史计划都不是触发器。没有独立发布指令时，不得修改 `main`、建立预发布候选、生成生产包或操作远程环境。

发布负责人按[独立发布流程](release-workflow.md)冻结准确 `develop`、核对 Git 中的开发回执与实际差异、运行发布侧集成 E2E、准确合入 `main`、完成 `main` 预发布，再按唯一 `subject + releaseType` 分类和打包。生产动作还须有目标网站和环境适用的明确授权，并遵守[发布架构](release-architecture.md)、[网站登记](site-registry.md)和目标网站运行手册。

发布侧发现代码缺陷时写阻断回执并退回 Gate8，不能在发布 worktree 直接修改业务实现。发布候选、预发布、管理员包、服务器动作和最终验收分别记录；任何阶段通过都不自动授予下一阶段动作。

## 8. D23 及历史记录

D23 仍负责其策划、内容、视觉和独立业务验收，D16 只消费当前有效批准入口。旧证据文件中的阶段编号和字段按生成时合同解释，保留为历史证据；它们不建立当前 D16 的额外角色、共享分支队列或生产权限。

Poland 交接实例、D23 模板和旧 Evidence Manifest 可用于理解已有记录，当前任务仍以本文件、根规则和用户最新裁定为准。
