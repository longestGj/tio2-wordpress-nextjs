# 第二阶段：最小内容发布改造

状态：用户已批准以下范围；本文将讨论结论固定为实现依据，尚不表示代码已实现或生产已安装。

开发基线：`develop` / `db36592574dc4847f9dae456ea36b9d9a984b2f8`。
任务分支：`codex/phase2-tio2-my-content-release`。

## 1. 目标与范围

复用现有发布程序，以网站配置驱动发布；让 `tio2-my` 的既有 CMS 页面内容可以独立于前台代码更新。数据发布前暂停共享 CMS 写入并备份整个数据库，发布失败时立即恢复整库。

保留一个共享 WordPress、一个共享数据库和现有通过 `SITE_ID` 绑定前台实例的结构。第二个网站复用程序，通过登记和配置接入，不复制一套发布程序。通用配置路径以第二个测试网站验证，但不解冻 Site B 业务或自行部署新网站。

这次开发不实现内容 generation、活动内容指针、网站范围备份、任意历史时刻单站回退、WordPress Multisite 或按 Host 动态切换网站的前台运行时。

开发以测试、独立代码复审、合入 `develop` 和开发回执为终点。生产安装及正式发布由独立发布任务执行。本任务不修改根 `AGENTS.md`。

## 2. 发布程序：配置驱动，复用控制器

沿用现有主体登记、固定动作、全局发布锁、包哈希、日志与回执。客户端从连接配置读取 `siteId`，服务端以可信登记校验主体，候选必须属于同一网站。严格验证网站 ID，不能把任意路径或命令交给 SSH。

重点修改 `scripts/production/Production.Core.psm1`、`scripts/production.ps1` 和 `ops/production/server/` 中实际固定 `tio2-my` 的运行入口与基线读取。历史接管兼容代码保持其原来的网站和候选限制，不用全局文本替换扩大权限。

网站的域名、端口、运行目录、容器和配置来自登记；不同网站复用同一适配器。新增站点的真实域名、证书和运行实例配置属于该站接入，不作为第二阶段预建任务。服务端仅接收明确登记的网站，客户端不能凭一个新 siteId 自行获取权限。

内容包为声明式数据，绑定网站、现有页面身份、结构版本、有序记录及内容哈希。不得把可执行 seed、SQL 或 Shell 当作可上传的任意生产程序。备份 SQL 由服务器生成并与本次发布绑定，恢复只使用该受控备份。

## 3. CMS 与前台：解除正文绑定，保留校验

WordPress `includes/*-v*.php` 和 Next.js `lib/wordpress/*-dto.ts` 当前存在把 CMS 正文与仓库 JSON 全文比较的逻辑；部分 DTO 直接返回编译进镜像的内容。逐类核对并改为从经校验的 CMS 数据生成页面。

保留网站归属、固定页面身份、URL、支持的 schema、字段类型、必填项、链接/HTML 安全规则，以及证据公开范围、禁止公开字段等业务约束。不能仅删除比较语句而放弃结构或安全检查。内容哈希证明内容一致性，不代替业务批准；批准依据由发布输入和回执绑定。

仓库 JSON 继续作为内容输入及测试夹具，不再作为已升级页面运行时正文必须逐字相等的唯一版本。保持现有 GraphQL 字段形状，不引入新的内容 CPT 或查询版本指针。

本次独立内容发布覆盖现有 CMS 页面类型内的内容。新增页面类型、路由/页面身份变化、Schema 变化、代码内导航、静态资源以及表单收件配置继续走相应代码发布。实际页面清单从当前登记与查询链路核对，不能把历史 42、56 或 58 的计数直接作为当前内容包清单。

## 4. 数据发布与恢复

对外保持测试、发布、回退三项操作；复用底层固定动作，内部步骤由程序完成。

1. 测试：同一不可变内容包导入隔离测试 CMS；读取并规范化导入后的内容，验证哈希、页面及关系。正式预发布仍由发布负责人从冻结的 main 建立。
2. 发布前校验包和测试依据，取得全局发布锁，暂停共享 CMS 的正常写入。暂停对象包括后台编辑、API 和其他自动写入者，单纯的发布进程锁不等于停止 CMS 写入。
3. 在写入暂停后生成完整共享数据库备份，确认备份可用；备份失败则不导入。保存发布前配置和前台版本身份，内容发布本身不修改这些版本。
4. 通过固定导入程序只更新包所属网站的数据；按稳定页面身份查找目标记录，不复制本地文章 ID、分类 ID 或临时 seed 状态。
5. 导入使用数据库事务；提交前校验规范化内容哈希。禁止逐条发送缓存 webhook，整包提交后统一刷新受影响路径、标签和 sitemap。
6. 对目标网站使用短暂维护窗口覆盖数据变更、缓存刷新和公开读取验证，避免实时读取与缓存页面显示不同版本；不要求所有网站前台一同维护。共享 CMS 的写入暂停仍覆盖所有网站。
7. 验证成功后完成回执并恢复正常写入和目标站访问。失败时保持写入暂停，使用本次整库备份恢复，刷新受影响缓存，验证恢复状态后再开放。恢复失败保持维护状态并记录失败，不能宣布已回退。

写入暂停和恢复进度须保存在现有事务日志中，断线后依据日志续接，不能盲目重新导入或重新备份已经改变的数据。恢复过程要验证完整共享数据库，包括其他网站发布前的数据仍存在。

整库恢复仅承诺本次发布窗口内的失败恢复。发布完成、正常写入恢复之后，默认用修正内容进行新发布；不开放会覆盖后续更新的自动历史整库回退。

数据库不包含上传文件。沿用现有媒体时无需重新复制；涉及新增或替换文件时，包必须显式列明文件，保存可恢复的旧文件及校验值。未具备相应文件处理能力的包在写入前拒绝，不能只恢复数据库就报告文件也已恢复。代码发布继续保存上一版代码/镜像。

## 5. 最小验收

- 配置为测试网站时，命令、传输目录和回执均属于该网站；未知网站、跨站候选和恶意 ID 被拒绝，不回退到 tio2-my。
- 修改一段合法 CMS 正文后，不重建前台即可看到新内容；身份、Schema、禁止公开数据或不安全链接变化仍被拒绝。覆盖所有实际改动的页面校验器。
- 包在隔离环境导入后，规范化内容与包哈希一致；跨环境 ID 差异不改变正文和关系。
- 在隔离的真实 WordPress/MariaDB 环境设置至少两个 scope。发布 A 的内容时 B 保持原样；备份后注入导入失败和验证失败，实际恢复整个数据库，验证两个 scope 均回到备份时刻。
- 后台/API 写入在窗口内被阻止；缓存通知只在批次完成后执行；成功发布及失败恢复均验证页面内容、状态、SEO 和 sitemap。
- 在备份、导入、提交、缓存刷新和恢复边界模拟中断，验证不会丢失恢复所需备份或提前恢复写入。模拟测试不能代替真实数据库恢复演练。
- 共享消费者做定向回归；新内容不得改变其他网站查询、表单收件、导航或冻结业务行为。开发测试不发送真实邮件。

## 6. 文档与既有实现的关系

本设计是本次用户简化决定的记录，替代原五类发布设计中第二阶段必须采用 generation、网站范围备份及独立历史内容回退的前提。原设计的阶段一事实、固定权限入口和现有生产回执继续按原范围解释。

代码完成前，网站登记中的 `content-only = not-installed` 保持不变。实现验收和生产安装分别记录；本地代码通过不能改写成服务器已经支持。

实现工作按三个交付单元组织：配置驱动的发布入口；CMS/前台内容读取解耦；整库备份、导入、恢复及端到端验证。每单元先写失败测试，再实现及回归，最终统一复审。
