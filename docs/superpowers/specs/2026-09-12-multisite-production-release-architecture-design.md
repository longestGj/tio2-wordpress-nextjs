# D16 多网站生产发布架构设计

**状态：** 设计方向已于 2026-09-12 获用户确认，等待书面设计复核  
**适用范围：** D16 管理、部署和发布到同一台或多台服务器的网站  
**首个迁移对象：** `tio2-my` 及其 `tio2malaysia.com`、`www.tio2malaysia.com`、`cms.tio2malaysia.com` 入口  
**现有生产候选：** `8bf2a3d437b0582ef0ce193b69478622e26419af`

## 1. 背景与问题

当前 TiO₂ Malaysia 固定发布程序是单网站实现。站点身份、域名、目录、容器、端口、证书、Nginx 文件和状态目录均写死为 `tio2-my`。首次接管时，生产基线登记了新前台的 Nginx 配置和主域证书，但保留中的 CMS Nginx 配置及 CMS TLS 依赖没有进入日常备份基线。当前候选已进入服务器 `PREPARED`，固定备份因此在写入停止前失败；公众仍使用旧版本，没有发生切流。

`tio2malaysia.com` 与 `cms.tio2malaysia.com` 是两个服务入口，但共同属于一个业务网站和一个发布单元。未来新增的独立业务网站必须拥有自己的代码、CMS、数据、配置、证书、状态、备份和回退边界。将整台服务器所有 Nginx 和 TLS 文件都登记到 `tio2-my` 会造成以下问题：

- 新增或更新其他网站会阻断 `tio2-my` 发布；
- 一个网站的备份会包含其他网站的证书私钥；
- 单站回退无法说明主机公共配置和其他站点的责任；
- 证书正常续期会被误判为基线篡改；
- 单一状态机无法独立表达多个网站的候选和活动版本。

本设计把现有发布程序改为“一个服务器控制面、多个独立网站发布单元”。

## 2. 目标与非目标

### 2.1 目标

1. 一个固定发布程序承接多个已由 root 登记的网站，不为新增网站复制核心发布代码。
2. 每个网站独立准备、备份、部署、验证、回退和封存回执。
3. Nginx 公共配置、网站专属配置和动态证书具有明确归属。
4. 发布一个网站时不读取、导出或修改其他网站的私有数据和私钥。
5. 未登记的 Nginx 配置、域名、端口、容器或文件继续失败关闭。
6. 保持 deploy 用户只调用固定动作；路径、命令和容器身份仍由 root 配置决定。
7. 将现有 `tio2-my` 在不移动数据、不修改 Nginx 内容、不重载和不切流的情况下迁入新架构。
8. 保留当前候选、当前 `PREPARED` 状态和同一个本地 RunRoot，迁移成功后恢复原发布批次。

### 2.2 非目标

- 本轮不把多个网站合并到同一个 Next.js 应用、WordPress 实例或数据库。
- 本轮不实现多个网站同时切流；第一版使用服务器全局发布锁串行执行。
- 本轮不迁移现有 WordPress 数据卷、数据库或活动发布目录的物理位置。
- 本轮不改变业务内容、域名、DNS、表单收件配置或网站视觉。
- 本轮不引入 CI/CD；它仍按已约定在本次生产发布完成后单独设计。

## 3. 核心概念

### 3.1 服务器

服务器是运行一个或多个网站的宿主机。服务器控制面拥有公共 Nginx 配置、公共 TLS 参数、端口登记、全局锁、已登记网站列表和固定发布程序版本。

### 3.2 网站发布单元

网站发布单元由一个 `siteId` 唯一标识，包含：

- 一个公开网站及其别名域名；
- 零个或一个 CMS 入口；
- 本网站使用的前后台运行时、数据库和持久卷；
- 本网站专属 Nginx 配置、上游配置和 TLS 身份；
- 独立候选、活动版本、备份、状态、审计和回退依据。

`tio2-my` 的公开入口与 CMS 入口属于同一发布单元。CMS 在普通前台发布中必须保持连续，但其数据和配置仍进入该网站的备份边界。

### 3.3 公共资源

公共资源由服务器控制面管理，例如：

- `/etc/nginx/nginx.conf`；
- `mime.types` 和已加载模块配置；
- Certbot 公共 TLS 选项；
- 共享 DH 参数；
- 发布程序、sudo 规则和服务器端网站登记。

公共资源有自己的固定指纹。公共资源变化必须经过 root 级服务器升级，不能由某个网站的日常发布顺带修改。

## 4. 目录与记录

### 4.1 新网站使用的标准目录

```text
/etc/d16-release/
  host.json
  host-baseline.json
  sites/
    <siteId>/
      site.json
      baseline.json
      production.env
      upstream.conf

/opt/d16-release/
  program -> programs/generation-*/
  programs/
  state/
    release.lock
  sites/
    <siteId>/
      current
      releases/
      backups/
      state/

/home/deploy/d16-incoming/<siteId>/
/home/deploy/d16-outgoing/<siteId>/
```

`siteId` 必须匹配 `[a-z0-9][a-z0-9-]{0,62}`，并且必须精确存在于 root 所有、不可组写或全局写的网站登记中。调用者不能提供路径。

### 4.2 `tio2-my` 兼容迁移

为避免在正在进行的生产发布中移动活动文件，首轮迁移允许 `tio2-my` 的 root 登记继续指向现有路径：

```text
/etc/tio2-production
/opt/tio2-production
/home/deploy/tio2-incoming
/home/deploy/tio2-outgoing
```

这些路径由迁移记录显式绑定，不通过调用参数选择。未来网站直接使用标准目录。现有路径是否物理迁移，在本次生产发布封存后另行决定。

## 5. 固定命令与权限边界

统一入口为：

```text
/usr/local/sbin/d16-release <siteId> <action>
```

动作保持关闭集合：

```text
status prepare backup deploy verify rollback
```

sudoers 为每个已登记网站逐项生成准确命令，例如：

```text
deploy ALL=(root) NOPASSWD: /usr/local/sbin/d16-release tio2-my status
deploy ALL=(root) NOPASSWD: /usr/local/sbin/d16-release tio2-my prepare
```

新增网站需要一次 root 接管操作，以写入网站登记和准确 sudoers 条目。日常 deploy 用户只能传入已登记 `siteId` 和固定动作，不能传入目录、主机名、端口、容器、证书、命令或环境变量。程序清空调用环境并从 root 登记解析全部资源。

## 6. Nginx 归属模型

### 6.1 完整登记

服务器登记必须覆盖 `nginx -T` 实际加载的每个配置文件。每个规范化真实路径只能有一个归属：

- `host`：服务器公共配置；
- `site:<siteId>`：某个网站专属配置。

未知文件、重复归属、不可解析路径、非 root 所有、符号链接逃逸、组写或全局写文件均阻断发布。逻辑 include 路径与解析后的真实路径同时记录：逻辑路径用于核对实际 Nginx 装载，真实路径用于读取、哈希和备份。

### 6.2 网站专属配置

网站登记列出准确域名和准确 Nginx 配置入口。接管程序解析实际配置并验证：

- 专属文件中的 `server_name` 只包含本网站域名或已登记的本地验证入口；
- 不允许一个专属文件同时承载两个网站；
- 专属 upstream 只指向本网站已登记端口；
- 本网站配置不能引用其他网站的证书或私有路径；
- 所有专属文件进入本网站配置备份。

如果现有文件混合承载多个网站，接管失败，并要求先由 root 将配置拆分为一站一文件。

### 6.3 日常检查

发布任一网站时：

1. `nginx -T` 的配置成员集合必须与服务器登记完全一致；
2. 公共文件字节必须与服务器公共基线一致；
3. 目标网站专属配置必须与其网站基线一致；
4. 其他网站文件只验证存在、root 保护和归属，不读取其私钥或纳入本次备份；
5. `nginx -t` 必须对整台服务器成功；
6. 切流只原子更新目标网站的 upstream 文件，然后执行一次全局 Nginx 重载。

其他网站的正常候选、数据或证书变化不会改变目标网站的发布状态。未登记文件仍会阻断所有发布，直到 root 完成接管登记。

## 7. TLS 与证书续期

证书不能按长期固定 SHA-256 管理，因为 Certbot 续期会改变 archive 文件和 `live` 软链接目标。网站登记保存稳定的证书身份策略：

- 证书名称；
- 允许的 `live/<cert-name>/` 逻辑路径；
- 允许的 `archive/<cert-name>/` 解析目录；
- 必须覆盖的 DNS 名称；
- 最低剩余有效期；
- 公钥与私钥配对验证方式。

每次备份在锁内解析当前软链接，拒绝目录逃逸，核对证书域名、有效期和密钥配对，然后把当前证书链与私钥字节纳入目标网站加密备份。回执记录当次解析路径和哈希，不把动态证书哈希写成永久网站基线。

Certbot 公共选项和 DH 参数归服务器公共基线；某个网站的证书及私钥只归该网站。发布和备份一个网站不得打开其他网站的私钥。

## 8. 运行时、数据与端口隔离

每个网站登记自己的运行时适配器。第一版支持当前已实现的 WordPress、MariaDB 和 Next.js 蓝绿发布模型，同时保留适配器字段，避免要求未来网站共用相同拓扑。

网站登记必须绑定：

- 前台与 CMS 容器身份规则；
- 数据库名称和数据库容器；
- WordPress 媒体卷与数据库卷；
- 构建镜像和 WP-CLI 工具镜像；
- 活动与候选端口；
- CMS、内部代理和健康检查端口；
- 插件源及其保留策略。

服务器接管时检查所有已登记端口唯一。所有应用端口默认只绑定 `127.0.0.1`，公网流量只通过 Nginx。一个网站的备份只停止该网站登记的写入者，不停止其他网站。

第一版使用服务器全局发布锁，保证备份、切流、Nginx 更新和回退串行发生。每个网站仍有独立状态目录；以后如有并发发布需求，可以在不改变状态格式的情况下增加站点锁和短时 Nginx 全局锁。

## 9. 网站状态与回执

每个网站保持独立状态机：

```text
IDLE
PREPARED
BACKED_UP
INTERNAL_VERIFIED
PUBLIC_VERIFIED
FAILED
ROLLED_BACK
```

所有状态和回执至少绑定：

- `siteId`；
- 候选 commit、archive、manifest 和 prerelease proof；
- 活动网站基线；
- 服务器公共基线版本；
- Build ID、CMS 身份和发布表面；
- 本网站备份与离机恢复证据；
- 部署、公开验证和最终验收证据。

服务器公共基线变化使所有尚未开始的发布重新准备。已经进入 `PREPARED` 的发布只能通过 root 迁移事务更新公共基线绑定，日常 deploy 命令不能自行改绑。

## 10. 备份边界

目标网站备份包含：

- 目标网站数据库逻辑备份；
- 目标网站 WordPress 文件及已登记外部挂载；
- 当前活动前台版本；
- 目标网站专属 Nginx 配置和 upstream；
- 目标网站当前证书链和私钥；
- 网站登记、网站基线、活动身份和发布状态；
- 公共基线身份及恢复所需公共文件的非秘密副本或引用清单。

服务器公共备份包含公共 Nginx 配置、Certbot 公共选项、DH 参数、发布程序、网站登记和 sudo 规则。它是 root 级主机维护动作，不在每次网站发布中重复导出。

网站备份不能包含其他网站的数据库、媒体、运行时配置或证书私钥。离机导出保持加密，恢复演练必须验证目标网站备份与其引用的公共基线可以共同恢复。

## 11. `tio2-my` 迁移事务

本次迁移由一个 SHA-256 绑定的管理员包完成。它只执行以下固定步骤：

1. 原子安装支持多网站的服务器程序，保留上一程序代；
2. 读取现有 root 基线、发布状态和首次接管记录；
3. 读取 `nginx -T`，定位只承载 `tio2malaysia.com`、`www.tio2malaysia.com` 和 `cms.tio2malaysia.com` 的配置；
4. 将 Nginx 主文件、模块、mime、Certbot 公共选项和共享 DH 参数登记为服务器公共资源；
5. 将前台配置、CMS 配置、upstream 和两套证书身份登记到 `tio2-my`；
6. 验证没有未知配置、混合网站文件、端口冲突或跨站 TLS 引用；
7. 写入迁移日志后，原子安装服务器登记和网站基线；
8. 将现有 `PREPARED` 状态中的活动基线与公共基线绑定更新为迁移后身份，同时保持候选身份、候选目录和本地 RunRoot 不变；
9. 运行只读状态验证和备份前置检查；
10. 删除迁移日志并输出不含秘密的迁移回执。

迁移不重写 Nginx 内容、不调用 reload、不修改容器、不停止 WordPress、不移动数据、不部署候选、不执行 DNS 或公网切流。

若任一步失败，程序利用迁移日志恢复旧程序指针、旧基线、旧状态和旧 sudoers。重复执行同一管理员包必须得到同一登记结果，并能完成中断恢复。

## 12. 当前生产发布的恢复方式

迁移成功后继续使用本地 RunRoot：

```text
.production/runs/20260911T215847Z-8bf2a3d437b0
```

执行顺序保持：

1. `Status` 核对 `tio2-my` 仍是旧活动版本、候选仍为 `8bf2a3d...`、状态仍为 `PREPARED`；
2. 使用相同 RunRoot 重试固定 `Release`；
3. 生成目标网站完整加密备份并完成真实解密/恢复验证；
4. 完成候选内部构建和 Gate B；
5. 切流并完成服务器 `PUBLIC_VERIFIED`；
6. 执行 58 对象、174 浏览器案例的生产 E2E；
7. RFQ、Sample、Documents 各执行一次已授权的真实提交；
8. 用户按唯一令牌确认三封生产邮件；
9. 封存最终 `PRODUCTION_VERIFIED` 回执。

多网站工具提交留在 `develop`，生产应用版本仍单独报告为 `main` 的 `8bf2a3d...`，避免把工具版本误报为网站版本。

## 13. 失败处理

- 公共配置未知或漂移：所有网站发布停止在写入前，等待 root 接管或公共基线升级。
- 目标网站配置漂移：只阻断目标网站发布。
- 其他网站配置字节变化：不改变目标网站状态；整机 `nginx -t` 仍必须通过。
- 证书正常续期：按网站证书策略重新验证并备份，不要求修改永久基线。
- 证书域名、路径或密钥不匹配：阻断对应网站发布。
- 迁移中断：下次执行先按日志恢复或完成，不接受部分登记。
- 备份失败：写入者必须恢复，候选不能切流，继续使用同一发布批次重试。
- 切流后失败：只回切目标网站 upstream，不改动其他网站。

## 14. 验证要求

实现必须使用 TDD，并至少覆盖：

1. 服务器公共文件、网站专属文件和未知文件的完整归属解析；
2. 两个模拟网站之间的配置、TLS、数据、状态和备份隔离；
3. 发布 A 不读取或归档 B 的私钥；
4. 其他网站字节变化不使目标网站基线失效；
5. 公共配置漂移和未知 Nginx 文件在停止写入前失败；
6. Certbot 软链接合法续期通过，目录逃逸、错误 SAN、过期和密钥不配对失败；
7. 一个配置文件承载多个网站时接管失败；
8. 端口冲突、容器跨站复用和卷跨站复用失败；
9. `PREPARED` 状态迁移保留候选身份并更新准确基线绑定；
10. 管理员安装和迁移在每个切换点中断后可恢复；
11. 网站备份归档成员不包含其他网站资源；
12. 当前生产 Python 套件、基础设施测试和隔离 Linux 发布演练通过；
13. 管理员包由准确 Git commit 构建，两次构建字节一致并记录 SHA-256；
14. 生产迁移后先执行只读核验，再恢复同一 RunRoot。

## 15. 新网站接入流程

未来新增网站时执行一次接管流程：

1. 在 D16 网站登记中确定 `siteId`、公开域名、CMS 域名和运行时方案；
2. 在开发环境完成网站及分层测试；
3. 在预发布环境完成完整 E2E 和批准；
4. root 探测目标服务器并生成只读接管计划；
5. 用户确认计划中的域名、端口、容器、卷、Nginx 和证书归属；
6. root 执行固定接管程序，创建目录、网站登记和准确 sudoers 命令；
7. deploy 用户完成首次备份、内部验证、切流和生产验收；
8. 封存该网站独立的生产回执。

新增网站不会修改其他网站的业务基线，也不会自动获得其他网站的发布授权。
