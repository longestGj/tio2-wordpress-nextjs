## 1. 本次修正与范围

本设计将 W3-A1 的“原写入校验完全不变”修正为“保留内容批准、权限、身份及安全约束，将旧稿比较从本批通用技术写入规则中移出”。不是用读取校验替代审批，也不是删除写入保护。

范围限于 `tio2-my` HOME-001 `/`、APP-000 `/applications` 及其普通 CMS 保存、受控批量导入和直接更新依赖。其他页面族、Site A/B 继续原有规则。共享外壳留 W3-A2；不新增审批后台、内容版本指针、数据库拆分或部署系统，不新增媒体、导航或业务事实。

现场最小比较已经证明：原写入 matcher 接受登记位置的标题、正文和 SEO 变化，但拒绝 `company.summaries` 从 3 项变为 4 项；首页 meta 更新后的强制校验将记录改为 draft。不能将其误述为所有文字都必须逐字相同。

## 2. 选择与职责

选择“技术校验 + 独立批准核验 + 写入适配”。不选择只放开数组比较：仍然保留旧稿作为结构模板；不选择只用技术 schema 放行：不能代替业务批准。

| 部分 | 输入与职责 | 输出与禁止事项 |
|---|---|---|
| 内容技术校验 | 页面身份、候选内容、已安装 schema；校验类型、必填、边界、关系和安全 | 返回明确成功/错误及经过验证的内容；不判断业务批准 |
| 批准核验 | 受控来源的批准依据、目标网站/页面、准确候选版本、当前版本与操作权限 | 返回本次精确内容操作的允许/拒绝；不信任内容包自称已批准 |
| CMS 写入适配 | 调用前两项，检查实际记录与并发条件，再执行对应保存/发布 | 写入、读回及事件结果；技术合法不自动获得发布权限 |
| 前端 | 读取已发布的技术有效记录，呈现正文与 SEO | 不重复查询历史批准稿、不承担编辑审批 |
| 构建 | 编译、检查代码/配置及内容兼容性 | 生成制品与证据，不批准内容 |

内容技术核心可供 PHP 读写共用；记录守卫分别适配草稿、公开读取、更新和发布。不得直接把只接受 publish 的读记录函数当作通用写入函数。

## 3. 批准依据及信任边界

批准决定来自用户或所属策划流程，D16 负责核对和执行，不创建业务批准。复用现有交付/候选材料承接批准依据，不开发新的审批系统。

批准核验至少绑定：批准来源及可核对的记录、目标网站/页面/语言、候选内容的确定性摘要、允许的操作，以及实际执行权限。当前内容摘要用于更新前条件检查，不以最后修改时间代替版本一致性。

- 摘要只标识内容版本，不证明批准；材料中的 `approved=true`、packageId 或 reviewId 都不能自行授予权限。
- 批准依据从受控入口独立取得；不能由待写入包指定任意批准文件、函数、SQL、数据库 ID 或可执行代码。
- 候选在批准后变化，摘要不符，拒绝操作；内容中的跟踪编号不构成豁免。
- 目标网站、页面、语言或操作不符，拒绝；相同文案跨站也不复用批准。
- 执行时重新核对授权仍有效；无法确认批准来源或有效性时失败关闭，不默认为允许。
- 批准内容不等于允许修改真实环境；目标环境和允许动作继续依独立操作授权。

这是一项核验接口要求，不宣称已有材料都能自动满足它。实施计划须从现有候选/交接接口确定受控输入格式与验证方法；不得以“文件存在”代替批准核验，也不得自行补签批准。隔离测试使用明确标注的合成批准材料，只能用于测试环境。

## 4. 保存与发布状态

候选内容 → 技术校验 → 批准准确版本 → 写入前核对权限、批准及当前内容 → 写入与读回 → 成功事件 → 页面更新验证。

草稿修改与发布是不同操作：草稿按现有权限和本批技术规则保存，不因合法而自动发布。编辑已发布页面时，未批准的候选不得覆盖公开内容；可在现有草稿能力范围准备候选，本批不承诺新增完整可视化编辑后台。

对本批受支持入口，在修改公开内容前完成检查。候选被拒绝时，当前有效内容和发布状态保持不变；不能先覆写再用降草稿处理正常的审批拒绝。当前版本已被其他操作改变时停止，重新形成差异并核对批准适用性，不覆盖新内容。

候选校验和最终写入之间仍需版本一致性保护。并发核对必须覆盖最终提交边界，不能只在请求开始时比较一次。批量操作任一页面不满足条件时，不提交部分内容。

真正非法的已存记录仍需现有防御性检查；本次不保证任意直接 SQL 或越权管理员修改能够被 WordPress 钩子提前阻止，不把测试入口包装成数据库安全边界。

## 5. 两类写入适配

### 普通 CMS 保存

适配本批记录相关的保存、状态变化和 meta 更新入口。对受保护内容写入使用写入前守卫；批准核验的结果只能约束本次精确网站/记录/字段/内容及操作，不能设置通用的跳过校验开关。

成功后读回确认内容和状态，再走现有签名事件与缓存刷新。被拒绝或未实际改变公开内容的候选不能发出“新版本已发布”成功事件。更新内容项数不能触发旧稿形状匹配而意外撤回合法页面。

### 受控批量导入

现有 `wordpress/release/release.php` 使用固定字段的直接数据库更新，避免逐记录 WordPress 钩子；保留其事务、维护窗口、整库备份、读回和恢复边界，不强改为逐条普通 CMS 保存。

本批候选改用相同的独立技术校验及批准核验。注册表只定位受控页面和字段，不能继续通过旧稿比较拒绝已经合法更新的记录。对象序列化不得恢复旧数组数量，哈希与实际写入内容必须一致。

提交成功后由批量发布流程执行对应站点的缓存刷新与页面验证；不在 SQL 导入器内重复补发逐条钩子事件。原有其他页面 validator 保持原行为，混合批次分别校验，不向未迁移页面传播放宽规则。

## 6. 失败与恢复

- 校验、批准或版本冲突：写入前拒绝，保留当前有效版本，返回明确原因。
- 写入或读回失败：按对应适配器的原子性/补偿边界处理，不报告成功；补偿前核对所有权和版本，不能覆盖并发的新内容。
- 数据已提交但缓存通知失败：分别记录已提交版本与通知失败，不盲目重写内容；重试通知须可核对事件身份。
- 接收刷新事件不等于缓存已失效，失效调用也不等于页面已输出新版本，三者分别记录。
- 批量发布仍在有效维护窗口内失败时沿用现有恢复机制；窗口关闭后不得自动恢复历史整库备份。

不新增内容版本指针或独立数据库。备份、回退及前端与内容 schema 兼容性约束继续有效。

5. 普通事件与批量刷新适配、失败记录、W3-A1 真实运行测试和必要文档。

本批不自动批准旧数据、不批量修改批准编号、不升级生产工具或安装服务器能力。此前读取/SEO/事件成果优先复用，只对新接口与受影响调用者复验。

## 8. 验收与交付

必须同时证明：

- 获批的准确内容版本可修改文字、SEO，并在技术上限内增减纯内容项，无需改前端代码。
- 未批准、批准后篡改、错站/错页、过期或无效授权、并发版本不符均不能发布。
- 技术无效内容即使带批准材料仍被拒绝；链接关系、政策、schema 和安全不能因审批放宽。
- 拒绝候选不改变当前有效内容/状态；写入或通知失败的证据与恢复行为可验证。
- 普通保存与批量导入分别执行真实隔离验证，不能以其中一条通过替代另一条。
- 修订 W3-A1 测试：通过真实受控批准写入上下文执行 meta-only 更新，钩子保持启用，不以未授权裸 meta 写入成功为验收目标。增加未批准写入拒绝用例。
- 同一 Build/进程下，两页各连续两轮合法变化，正文/SEO/结构化数据更新；记录事件与实际输出，并完成 390/1440 视觉及交互检查。
- 共享消费者及未迁移页面做有限回归，独立审查准确提交范围，合入 develop 后复验并更新回执。

业务批准、开发完成、验收通过、发布授权和已部署仍分别记录。文档获批只消除方案选择上的停顿，不消除已记录的真实失败；W3-A1 在实现与验收完成前仍不标记完成。
