## 3. 需在新计划关闭的关键问题

1. **接口生产者缺失。** 备份重构读取 `runtime-baseline.json`、`active-release.json` 或 `legacy-baseline.json`、数据库默认配置和固定 Compose，但建立这些可信输入的流程还没有打通。必须先完成基线导入与校验，再调用备份。
2. **阶段证据不足。** `BACKED_UP` 只能表示服务端备份结果；不能据此推断异地下载、解密、恢复演练或后续冻结写入已经完成。保留动作名称，在状态记录中明确这些门槛。
3. **备份与迁移之间的写入条件未证明。** 当前候选备份使用维护模式与固定等待，再恢复服务；它没有独立证明所有编辑、定时任务或其他写入者均停止。必须建立可验证的写入隔离；恢复写入以后，原备份不再具备自动无损回退资格。
4. **模板与真实拓扑仍脱节。** 例如构建使用 `http://wordpress/graphql`，必须实测 Docker 构建阶段的访问路径；不能把运行时 Compose DNS 当成构建时已经可用。插件绑定依赖 `current`，而 `current` 应表示现网版本，不能在候选验证前擅自切换。
5. **打包版本更新机制不完整。** PowerShell 中冻结了三份合同的文件哈希；迁移合同变化时必须同步经过评审的版本登记和测试，否则正确的新包也会被拒绝。哈希一致性与发布来源授权是两件事，需分别定义。
6. **备份重构仍需审核。** 临时凭据的崩溃清理、停止服务后的重启、发布文件与状态写入之间中断、活动回滚备份保留、资源峰值，以及全库备份的恢复范围都要验证。假工具结果不证明真实 MariaDB/Docker 行为成立。
7. **验证范围需要分层。** 当前本机 Python 假工具测试、静态契约、Linux 操作系统语义测试、真实容器演练、ARM64 镜像验证和生产验收各有独立证据。58 页面无提交检查不能代替真实表单收件证明。

## 4. 调整方案

选择“复用已有安全基础，接入实际部署结果，完成最小日常发布工具”。不推翻重写，也不继续把首次上线、服务器加固、自动迁移、日常升级全部塞进一次开发。

保留 Windows 本地控制器、root 管理的固定 Python 程序、六个动作和精确版本合同。实际环境和可信基线由部署窗口提供并核验；本窗口先以同形隔离环境开发。日常代码发布优先打通；CMS 数据变化必须携带本次批准的 Plan/Apply/readback 与兼容性依据，无数据变化的版本不重复 seed。

特权程序升级与网站代码发布分开管理；网站包不得替换 root 程序、sudo 策略或任意容器挂载。首版不增加签名服务、通用调度平台或新的常驻 Agent；在受控发布者模型下明确 SSH 上传者的信任范围，由固定程序约束动作和运行配置。若要防止发布账户自行构造未批准版本，需要另行决定独立签名/批准根，不能声称文件哈希已经解决。

## 5. 新旧范围对应

新计划包含四个开发交付任务：可验证基线与准备、可靠备份、受控更新与回滚、完整演练与操作入口。原任务 1–5 的成果被复用，任务 6 的重构继续验收，原任务 7–12 按上述四个结果归并。原任务 13 的共享分支集成需在开发完成后另行协调；原任务 14–17 的正式操作由另一个窗口负责，不纳入本窗口自动执行范围。

部署窗口需要提供非秘密交接：实际提交/镜像身份、Compose 与 Nginx 路径、服务与卷标识、健康检查方法、配置字段名和保存位置、最近备份/恢复结果、是否已允许公开和编辑写入。不得在文档中放密码、token、私钥或完整环境值。
