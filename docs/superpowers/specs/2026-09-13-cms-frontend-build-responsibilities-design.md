# CMS、前端、配置与构建职责划分

日期：2026-09-13。状态：用户已确认职责划分与总体改造方向；本次授权为保存文档、同步相关规则。不是实现完成、开发接单或发布授权。

## 1. 目的与范围

保留 Headless WordPress + Next.js 架构，按职责拆开内容、代码批准稿、功能配置与构建的绑定。批准决定什么可以进入已发布内容；读取决定内容是否符合技术要求，两者不能混为一谈。

本次整改以 `tio2-my` 为主。共享代码变更需核对 A/B 消费者，保持 Site B 冻结及 Site A 既有业务限制；不自动迁移其他网站，不变更业务事实、已批准 URL、视觉或行为。

问题依据见[内容耦合审计](../../verification/2026-09-13-tio2-my-content-coupling-audit.md)。该审计基于 main `e2883161`，不是所有开发分支或生产环境的当前状态。既有法律页解耦工作须按其实际交付与验证承接，不重复实现，不据历史进度宣称完成。

## 2. 职责边界

| 角色 | 应负责 | 不应负责 |
|---|---|---|
| CMS | 内容、SEO 文案、内容版本、发布状态及受控内容发布流程 | 前端组件实现、构建参数、部署权限 |
| 前端 | 按技术契约读取内容，呈现、交互、SEO 输出及安全检查 | 用代码内旧文案重新批准 CMS 内容 |
| 配置 | 网站身份、服务地址、密钥、功能开关、环境与授权策略 | 保存页面正文或充当内容批准稿 |
| 构建 | 检查代码与配置，编译、预渲染、生成可追踪制品 | 判断业务文案是否等于历史批准稿 |
| 发布流程 | 核对代码、内容版本、环境、验收与发布授权 | 让每次线上读取重新执行审批 |

CMS 是纳入管理的可编辑内容的运行时来源，不替代策划/用户的业务批准，也不意味着任意编辑者获准直接写生产。代码、路由规则、静态资产和环境配置仍有各自来源，不强制塞进 CMS。

## 3. 字段与契约分类

- **内容字段**：正文、标题、描述、按钮显示文字等，由 CMS 提供；读取不与历史文案逐字比较。
- **稳定技术身份**：网站、页面、语言、路由及记录归属，必须准确校验；修改身份仍须适用授权。
- **技术结构**：字段类型、必填项、支持的组件/块、协议和安全限制，按技术 schema 校验。schema 版本不等于内容批准版本。
- **动作语义**：稳定动作标识由前端白名单解释，显示文字不决定动作，不允许任意脚本或任意动作注入。
- **政策与授权**：披露范围、内容复审时效、功能启用及索引授权等独立建模，保留原约束，不因解耦删除。
- **审批证据**：批准包编号、快照、哈希和历史版本用于交接、验收、追踪及适用恢复，不作为运行读取时的旧文案相等门槛。

将原字段归类后才迁移；不能把所有枚举、数组长度和版本校验一律删除。受支持结构内的内容修改不应要求改代码；新增不支持的字段或组件结构仍属于开发。

## 4. 目标数据流与模块调整

### 4.1 内容读取与 SEO

受控内容发布 → CMS 已发布记录 → PHP/API 的身份、状态及技术校验 → 前端 DTO 技术校验 → 正文、metadata 与结构化数据。

PHP 和 TypeScript 移除读取路径上的历史正文、标题、批准包编号等机械相等要求，保留各自边界所需的身份、唯一性、发布状态及安全检查。不要以旧批准稿静默 fallback。

可编辑 SEO 标题、描述来自同一 CMS 内容；前端负责输出转换。站点域名、canonical 生成、索引授权和安全规则仍属于技术配置或政策。

### 4.2 交互与功能配置

按钮按稳定 action ID（如 `open-cookie-settings`）决定行为；翻译或改标签不改变功能。保留既有动作与允许目标。

统计功能分开表达环境 ID、网站/环境启用授权及访问者同意。法律页面解释政策，不承载技术开关；有 ID 不等于获准启用，有启用授权也不替代访问者同意。

配置逐项记录构建期、启动期或运行期生效方式。现有 `NEXT_PUBLIC_*` 构建固化机制可以保留；修改后需重建的字段必须明确，不强制引入新的动态配置服务。

### 4.3 页面身份与缓存刷新

同一网站的 CMS 事件、查询与刷新端复用一致的稳定页面身份映射；MY 产品总览/详情不能套用 Site A 的准入规则，跨站拒绝仍保留。

缓存主要按网站、页面及语言等稳定身份失效。内容修订号用于追踪；若保留修订标签，必须有跨修订失效路径，不能锁定某次批准编号。

刷新记录区分事件接收、缓存失效和页面已输出新版本。普通编辑与撤回/法律等敏感更新分别在实施任务中固定时效、失败处理及观察方法；未固定并验证这些条件，不能宣称更新链验收完成。接口 200 不代替实际页面验证。

### 4.4 构建、错误与恢复

保留构建时读取 CMS 的预渲染。技术结构兼容的合法内容变化应可正常构建；CMS 不可达、身份错误、数据损坏和不支持的结构应明确报错，不吞错或替换为旧批准稿。

制品及回执记录代码版本、配置标识、采用的内容版本依据和环境，不记录密钥。内容批准、构建成功、部署完成分别记录。

本方案不新增内容版本指针、数据库拆分或恢复机制。内容发布继续遵守现有维护窗口、整库备份和恢复约束；前端回退也必须核对目标代码与当前内容 schema 的兼容性，不能假设旧代码必然兼容新内容。

## 5. 分批实施边界

1. 固定字段职责、兼容范围和受影响消费者。
2. 承接法律页已有改造与验证；另修复 MY 产品刷新入口并分别验证。
3. 按页面族成套迁移 PHP、DTO、渲染、SEO 和刷新依赖。
4. 拆分功能配置、缓存版本及其余显示文字驱动行为。
5. 完成整链验收，按开发流程交付；发布由独立指令启动。

本节是总体顺序，不是可直接执行的任务清单。各批次开始前固定实际代码基线、文件范围、数据兼容/迁移方式、测试与恢复边界；不在未确认范围内同步改生产数据或配置。

选择分层迁移而非仅修报错点，是为了消除相同根因；不改为全面动态渲染，因为渲染时机变化并不能消除职责混杂。

## 6. 验收标准

- 在支持的结构内修改正文、标题、按钮文字及 SEO 后，无需改代码，按该批次约定时效生效；正文和 SEO 同步。
- 跨站、未发布、危险 URL/HTML、不支持的结构仍被拒绝，审批、披露、复审及功能授权不能被绕过。
- MY 产品总览、详情、混合刷新批次和受影响依赖正确处理；拒绝事件不得造成错误站点失效。
- 实际 WordPress → WPGraphQL → Next 页面链路验证正文、SEO 与交互，不能只使用 mock 或接口成功回执。
- CMS 不可用、配置缺失和刷新失败有明确可追踪结果；验证兼容内容能构建、非法技术输入会失败。
- 共享消费者有限回归，适用视口/交互实际查看；准确记录代码、Build、内容和环境身份。
