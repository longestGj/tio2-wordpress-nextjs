# CMS、前端、配置与构建解耦总实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to execute approved work packages with checkpoints. Steps use checkbox (`- [ ]`) syntax for tracking. 本文件是整体审查与交付控制计划；业务实现按各工作包的冻结文件清单和详细任务执行，不因本文件存在自动启动任务或发布。

**Goal:** 在 `tio2-my` 消除运行内容与代码批准稿的不当绑定，使合法内容更新能通过 CMS、前端和缓存链生效，同时保留审批、安全、站点隔离及发布权限。

**Architecture:** 保留 WordPress + Next.js 和构建预渲染；分离内容、技术 schema、稳定身份、动作、政策配置与历史证据。按页面族迁移，每族同时完成 PHP、DTO、呈现、SEO 和更新链，不采用整站一次性切换。

**Tech Stack:** 仓库锁定的 Next.js、React、TypeScript、PHP、WPGraphQL、MariaDB、Vitest 及现有隔离环境工具。

**Spec:** [已确认职责划分](../specs/2026-09-13-cms-frontend-build-responsibilities-design.md)。

**状态：** 2026-09-13 用户已同意整体计划，W0 静态基线梳理完成；W1 已完成承接，见 [W1 回执](../../verification/2026-09-13-cms-decoupling-w1-adoption.md)。W2 代码已独立复审并合入 develop `c3331199`，收口结果见 [W2 回执](../../verification/2026-09-13-cms-decoupling-w2-product-revalidation.md)。W3–W6 未完成。W0 历史基线见[W0 清单](../../verification/2026-09-13-cms-decoupling-w0-inventory.md)。

## 1. 总范围、约束与终点

- 覆盖[审计 C01–C09](../../verification/2026-09-13-tio2-my-content-coupling-audit.md)，不能以首批产品刷新修复代替整体交付。
- 范围包括 MY 当前公开页面、对应共享外壳/SEO、CMS 读取、技术配置和构建验证；共享修改只对 A/B 做必要回归，不改其业务批准内容。
- 保留业务批准、受控写入、唯一记录、网站/语言/路由身份、HTML/URL 安全、披露、时效、同意及索引授权。
- 不新增微服务、CMS 数据库拆分、通用页面搭建器、动态配置服务或消息队列；不强制所有静态资产和系统页面内容进入 CMS。
- 不批量删除校验，不引入静默旧批准稿 fallback，不把不可达/错误内容伪装成有效页面。
- 开发终点：所有适用工作包通过独立复审、准确合入 develop、有整体开发回执。生产安装、main 候选、预发布和部署仍由独立发布指令启动。

## 6. W3：按页面族完成读取、呈现与 SEO

每族独立冻结任务范围、红绿测试、兼容性和审查提交。不能“只放宽 DTO”或“只换 metadata”。

| 迁移组 | 范围与主要入口 | 特别保留的边界 |
|---|---|---|
| A | 首页 `homepage-v04-*`、共享外壳、应用中心 `application-hub-v01-*` | 导航身份、公开投影、跨页引用与布局结构 |
| B | About、Contact 对应 DTO/查询/组件 | 联系事实披露、真实事实批准；标签变更不使合法事实消失 |
| C | 产品总览、详情、氯化法及 editorial 工艺页面 | 牌号/路由身份、事实与产品关系；不靠批准正文哈希确定读有效性 |
| D | 市场总览、EU/UK/Poland、country、Brazil EN/PT | 多语言关系、canonical/hreflang；支持范围内段落不是固定批准稿元组 |
| E | 资源总览、origin/proc、其他 editorial 页面 | 证据来源、披露和有效复审；有效性政策不退化为全量历史证据相等 |
| F | Documents 总览、TDS/REACH/COO | 文件/媒体归属、公开状态、允许链接；不新增或替换文件 |
| G | RFQ、Sample、Request Documents 及关联状态页 | 内容与表单接收配置分离，收件、请求与成功判定不改变 |

W0 核对真实路由与 registry 后将别名或共用模板归入上述组；不以 DTO 文件数量代表页面数量。法律路由由 W1 覆盖。

**每组相同的完整交付步骤：**

- [ ] 从 W0 清单固定该组 PHP、schema、DTO、组件、SEO 和刷新文件，列出共享消费者。
- [ ] 先写接受安全内容变化、拒绝非法结构/身份的行为测试，确认旧实现的真实红灯。
- [ ] 分开读技术校验与写入批准校验；PHP/TS 使用同一技术含义和共享测试样例，未知字段按明确投影/拒绝规则处理，不静默漏掉支持的正文。
- [ ] 直接投影有效 CMS 内容，移除静态批准正文回填、标签/位置决定事实取值等逻辑；仍须满足披露与业务政策。
- [ ] 将可编辑 title/description、OG/Twitter 文案和适用 JSON-LD 文案接入同一 DTO。`tio2-my-publication-metadata.ts` 及 inventory 保留页面身份、canonical、语言和索引策略，不继续覆盖 CMS 文案。共享接口迁移时显式区分已迁移与未迁移调用者，不添加永久静默 fallback。
- [ ] 在真实隔离 WordPress 中使用合成、安全变化内容，观察正文、SEO、跨页依赖及更新后输出；CMS 更改不需要代码提交或重新批准代码。
- [ ] 运行相关单元/集成、少量关键 E2E，实际查看适用视口和交互；保存准确代码/Build/CMS 身份。
- [ ] 独立复审后交付该组，更新覆盖清单；不提前关闭其未通过的跨页/刷新事项。

**通过条件：** 每个迁移组能独立解释运行来源、技术检查与政策归属，并证明真实内容变化生效。已有测试的历史固定文案断言改为职责和行为断言，不能只删失败断言。

## 11. 审查点与实施纪律

1. 用户先审查本总计划的范围、顺序和完成标准；60 秒普通更新测试窗口是本计划新增建议，随整体审查确认，不改已有更严格政策。
2. 每个工作包开工前形成准确文件/接口、数据兼容方式、红绿测试和命令的详细任务。W2 已有详细计划；其他包依 W0 清单展开，不把本总计划冒充逐文件编码方案。
3. 结构或授权边界变化、未知 CMS 数据迁移或不可兼容回退，必须说明具体差异并暂停受影响步骤；不重复询问已批准的职责原则。
4. 每批真实验证、独立复审与合并记录可单独审查；不等所有代码写完才第一次集成。
5. 无实现前不勾选完成，不用文档完整、测试数量或上一批通过推断总体完成。
