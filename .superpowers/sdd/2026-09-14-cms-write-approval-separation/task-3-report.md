# Task 3 report — committed content events

Status: DONE_WITH_CONCERNS (local implementation verified; independent review and any later integration remain with controller).

## Implementation and interface

- `tio2_apply_approved_content` now prepares an eventful receipt in a dedicated, non-autoload WordPress option **inside its InnoDB transaction**, before COMMIT. `add_option` failure yields `write_receipt` and rolls back content; no-event receipts remain `not-needed` without transport. `tio2_release_approved_content_events(array $receipt, array $events): array` runs after COMMIT and context cleanup. Its result retains `committed=true`; transport/ack/outcome-persistence problems produce `notificationState=failed`, not content rollback.
- Per operation, only registered MY HOME-001/APP-000 post IDs and fixed paths are accepted. Their affected paths/entities are merged into one signed MY `contentRelease` request. Existing ordinary webhook sender/queue, A/B behavior and receiver code are unchanged. The release uses the installed endpoint/secret and receiver protocol (`eventId`, `modified`, HMAC, scoped `siteIds`, `contentRelease`); the latter requests `expire:0`, ordinary webhook events retain existing `max` behavior.
- The server-owned option holds version, installed environment ID, immutable receipt identity/digests/target post IDs, current payload and at most 16 attempt identities/results. It is not page content. The returned opaque UUID `receiptId` is the sole retry input. `tio2_retry_approved_content_events(string $receipt_id)` has no route/CLI/scheduler and requires a logged-in WordPress actor with edit and publish capabilities for every target. Retry reloads and validates the stored site, environment, fixed target type/slug/scope, paths, entities, digest and last attempt ID; caller cannot supply URL, payload or event target. A per-receipt MariaDB named lock serializes retries and outcome updates, separately from the already-committed content transaction.
- HTTP 2xx alone is not success: receiver JSON must return `ok=true`, the exact event ID and `contentRelease`, and array `revalidatedTags`/`revalidatedPaths`. 409, timeout/transport errors and malformed acknowledgements remain failed/uncertain, not delivered. An in-window retry uses the same body/event ID, so the receiver's same-body replay response is accepted as an acknowledgement, not proof of a new invalidation. After the receiver's five-minute timestamp window, retry persists a fresh event ID/timestamp under the same receipt before sending; old identity is retained. This can duplicate invalidation if a timed-out earlier request actually landed, and the receipt marks `retryMayDuplicateInvalidation`.
- An outcome-store failure after COMMIT returns `committed=true`, `notificationState=failed`, `notificationPersistenceUncertain=true`. The persisted pending/previous state can be retried, without content rewrite. Received/revalidated/rendered are not conflated; this task verifies only sender/receiver acknowledgements and focused receiver tests, not live rendering.
